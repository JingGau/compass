# 精简排查流程（低阶模型专用）

**本文件是完整排查流程的精简版，将所有步骤合并在一个文件中。**

适用场景：
- 运行模型上下文窗口较小
- 模型无法正确解析多个 YAML 文件
- 用户说「简单点」

> 高阶模型不要用这个文件，应走 SKILL.md 中的完整 8 步流程。

---

## 精简流程（4 步）

> **即使走本精简版**：Step 1～2 **禁止执行任何查询**；只有用户明确说「可以/开始」后，才进入 Step 3。

### Step 1 — 理解问题

从用户的描述中提取以下信息（能提取多少就提取多少）：

| 需要提取的 | 示例 |
|-----------|------|
| 手机号 | 138xxxx1234 |
| 用户ID | 123456 |
| 订单号/交易号 | ORD20260328001 |
| 时间范围 | 「今天下午」→ 今天 12:00~当前 |
| 问题描述 | 余额不对、充电卡住、支付失败… |

**判断场景**：
- 提到页面、后台、B端操作 → B端问题
- 提到充电、支付、App → C端问题
- 不确定 → 问用户

**选择排查方向**（只选 1 个，不做多方案）：

| 问题关键词 | 排查方向 | 用什么工具 |
|-----------|---------|-----------|
| 余额、钱包、显示为0 | 查缓存 + 查数据库 | Redis + MySQL |
| 支付失败、扣费、多扣 | 查交易记录 + 查日志 | Platform/MySQL + SLS |
| 充电卡住、无法结束 | 查订单状态 + 查设备日志 | Platform + SLS |
| 充值未到账 | 查支付回调 + 查资金流水 | SLS + MySQL |
| 页面报错、加载失败 | 查接口日志 | SLS |
| 发票问题 | 查发票记录 + 查日志 | MySQL + SLS |

### Step 2 — 展示方案并确认

**默认只用罗盘 `adapters/` 里的脚本查数**；不要用工作区里别的 MCP 或本机 `mysql` 直连，除非用户明确说要用。

若用户**一次给了多条关键信息**（例如既有订单号又有充值单号、或两个现象），用 **方案 A / 方案 B** 两行说明「先查哪条线、能回答什么问题」，让用户选 **A** / **B**，不要糊成一句「我帮你查查」。

用简单列表展示方案，等用户说「好的」「可以」再执行：

```
我来帮你查一下，计划如下：

1. 查缓存里的余额（Redis）
2. 查数据库里的实际余额（MySQL）
3. 查最近的操作日志看有没有异常（SLS）

可以开始吗？
```

**注意**：
- 不展示 SQL 语句、Redis 命令等技术细节
- 用「查缓存」「查数据库」「查日志」这样的自然语言
- 如果用户是技术人员（提到了表名/代码），可以展示具体查询
- **用户不表态 → 默认确认，直接开始执行**

### Step 3 — 执行查询（确认后全自动）

用户确认后（或不表态 → 默认执行），**自动执行全部步骤，中途不打断**：

```
✅ 第 1 步完成：缓存里余额是 0
✅ 第 2 步完成：数据库里余额是 200 元 — ⚠️ 和缓存不一致
⏳ 第 3 步执行中：正在查操作日志...
✅ 第 3 步完成：发现 2 小时前 refreshCache 超时失败
✅ 排查完成，正在生成结论...
```

**安全检查（简化版）**：
- 只执行 SELECT 查询，禁止任何写操作
- 手机号、身份证等展示时打码（如 138****1234）
- 单次查询最多返回 100 条

### Step 4 — 给出结论

```
查完了，结论如下：

问题原因：缓存中的余额数据过期了，显示的是旧值（0），
         实际数据库里余额是 200 元，是正常的。

建议操作：
1. 让用户退出重新登录，缓存会自动刷新
2. 如果还不行，联系开发手动清理缓存
```

## 工具使用速查

直接使用 MCP 工具，无需 Python：

| 工具 | MCP 工具 | 说明 |
|------|---------|------|
| Platform | `mcp__mysql-client__*` | Doris 查询（仅 prod） |
| SLS | `mcp__sls-client__query_logs` | 日志查询 |
| MySQL | `mcp__mysql-client__execute_sql` | MySQL 查询 |
| Redis | `mcp__redis-client__execute_command` | Redis 操作 |
| ES | `mcp__elasticsearch-client__es_search` | ES 搜索 |

---

## 重要约束

1. **禁止写操作**：只读查询，任何 INSERT/UPDATE/DELETE/DROP 都不能执行
2. **数据脱敏**：手机号、身份证、银行卡展示时打码
3. **用户确认**：方案确认前不执行任何查询
4. **一次只查一个方向**：不做多方案并行，降低复杂度
5. **有问题就停**：查询报错时告诉用户，不要自己重试或绕过

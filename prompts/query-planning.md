# 查询规划

**职责**：根据实体、场景，制定具体的查询方案，展示给用户确认后执行。

> 本文件被 SKILL.md Step 4 引用，核心约束以 SKILL.md 为准，本文件负责具体执行细节。

---

## ⛔ 执行前硬约束

1. **用户明确确认方案之前，禁止调用任何 adapter**
2. **单线顺序执行**，禁止并行方案、禁止父子 Agent
3. **仅用内部 Adapter**：通过 `adapters/<n>/client.py` 调用，禁止外部 MCP 工具
4. **空结果最多重试 3 次**，仍无结果停下来告知用户
5. **环境探查（Step 0）不得跳过**：未读各 adapter `config.yaml` 前，不得假设工具可用

## 执行模型

| 用户说 | 行为 |
|--------|------|
| 「好」「可以」「确认」「开始」 | 开始执行 |
| 意图不明确 / 无回复 | 默认走 0 号自动模式 |
| 「等等」「停」「先别查」 | **立即中断，保留已有结果** |
| 执行中发其他问题 | 先回答，再继续自动流程 |

**确认后自动执行规则：**
- 按方案逐步执行，不中途等待
- 三轨（代码/日志/数据）交织推进，任何一轨有新发现立刻带入下一步
- 空结果 → 自动换条件重查（最多 3 次）
- 得出结论 / 路径耗尽 / 需切换策略 → 停下来告知用户

### ▶ Step 2：三轨入轨声明（0号自动模式必做）

> 开始执行前，AI 必须先声明入轨方式，用户可以在此纠正方向，避免查了一半才发现跑偏。

**根据当前掌握的信息，从三种入轨方式中选一种：**

| 入轨方式 | 触发条件 | 第一步做什么 |
|---------|---------|------------|
| 🔵 代码先行 | 已知接口名 / 业务场景明确 / 有服务名 | 读接口代码 → 提取关键字/表名 → 带着发现查日志或DB |
| 🟡 日志先行 | 不知道接口，但有关键字（用户ID/订单号/交易号） | 宽关键字查日志 → 找到接口名/traceId → 读该接口代码 → 继续深查 |
| 🟢 数据先行 | 有明确异常数据表现，知道哪张表或哪个字段 | 关键字找相关表 → 看哪些接口写这张表 → 读代码分析逻辑 |

**声明格式（必须输出）：**

```
本次选择 [🔵代码先行 / 🟡日志先行 / 🟢数据先行]
原因：___
第一步将：___
```

> 用户可在此纠正入轨方式，确认后再执行。

---

### ▶ Step 3：三轨协作执行（核心）

> 三轨不是串行切换，而是**交织推进**——任何一轨有新发现，立刻带入最相关的另一轨。

**每一步查完后，必须问自己：**

| 自检问题 | 有发现时的操作 |
|---------|--------------|
| 日志指向代码了吗？ | 有 traceId / 接口名 / 类名 → 立刻去读对应代码 |
| 代码指向数据了吗？ | 有表名 / Redis key / ES index → 立刻去查对应数据 |
| 数据指向日志了吗？ | 有时间戳 / 操作记录 → 立刻缩小日志时间窗重查 |

**禁止行为：**

| ❌ 禁止 | ✅ 正确 |
|--------|--------|
| 某一轨查不到就埋头继续查同一轨 | 查不到时带着已有线索跳到另一轨 |
| 日志查完再读代码，代码读完再查数据（顺序割裂） | 日志里出现接口名 → 立刻去读代码，不等日志查完 |
| 空结果直接报告「没查到」 | 空结果 → 换条件 / 换工具 / 换时间窗，最多重试3次 |

**三轨典型协作路径：**

```
🔵 代码先行路径：
  读接口代码
    → 找到日志关键字（如 logger.info("adjustBalance...")）
    → 用关键字查 SLS
    → 从日志提取 traceId
    → 小时间窗拉完整链路
    → 链路中发现 DB 写失败
    → 查 MySQL 确认数据状态
    → 结论

🟡 日志先行路径：
  宽关键字查日志（userId / tradeSeq）
    → 找到接口名 / 类名
    → 读该接口代码，理解业务逻辑
    → 用代码中的关键字缩小日志范围
    → 发现 Redis 操作失败
    → 查 Redis 确认缓存状态
    → 结论

🟢 数据先行路径：
  关键字找到异常表（如 t_user_wallet）
    → 查表记录确认异常数据
    → 找哪些接口写了这张表（读代码）
    → 结合接口代码的日志关键字查 SLS
    → 定位到具体失败的操作
    → 结论
```

### ▶ Step 4：按需选择 Adapter

> 只选解决问题所需的工具，不是全部用上。根据三轨推进中的发现动态调整。

| Adapter | 适用场景 |
|---------|---------|
| sls | 查日志、拉链路、提取 traceId |
| mysql | 查业务记录（支付、订单、用户、钱包） |
| redis | 查缓存状态、验证缓存一致性 |
| platform (Doris) | 查统计数据、宽表 |
| elasticsearch | 补充全文检索 |

**代码嵌入时机（每次查询前先读代码）：**

| 查询前 | 读代码确认 |
|--------|-----------|
| 查 SLS 前 | 关键字、容器名、traceId 生成位置、日志打印格式 |
| 查 MySQL/Platform 前 | 表名、字段名、查询条件 |
| 查 Redis 前 | key 模式、过期策略 |

---

### ▶ Step 5：方案规划与收敛判断

> 单线推进，按证据驱动逐步执行。

**步骤五要素（缺一不可）：**

| 要素 | 含义 | 禁止写法 |
|------|------|---------|
| 目的 | 这一步要澄清什么 | 「查一下数据库」 |
| 工具 | adapter 名 | 「查库」（未指明） |
| 环境 | profile 名 | 「线上」（未映射） |
| 查什么 | 关键字、表/字段、key 模式 | 「看日志」 |
| 预期 | 看到什么算有价值 | 缺失 |

**收敛判断：**

| 状态 | 操作 |
|------|------|
| 三轨互相印证 | 给出结论，进入 result-analysis.md |
| 某轨缺失但其他两轨已闭环 | 标注「⚠️ 未证实」给弱结论 |
| 三轨都没线索 | 停下来告知用户，请求补充信息 |

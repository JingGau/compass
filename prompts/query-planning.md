# 查询规划

**职责**：根据实体、场景，制定具体的查询方案，展示给用户确认后执行。

> 本文件被 SKILL.md Step 4 引用，核心约束以 SKILL.md 为准，本文件负责具体执行细节。

---

## ⛔ 执行前硬约束

1. **用户明确确认方案之前，禁止调用任何 adapter**
2. **单线顺序执行**，禁止并行方案、禁止父子 Agent
3. **内部 Adapter 优先**：通过 `adapters/<n>/client.py` 调用；JDBC / 外部库须用户确认后才能使用
4. **空结果最多重试 3 次**，仍无结果停下来告知用户
5. **环境探查（Step 0）不得跳过**：未读各 adapter `config.yaml` 前，不得假设工具可用
6. **prod 环境 SQL 必须先 EXPLAIN**：通过后自动执行；危险则暂停等待用户确认

## 执行模式

| 模式 | 触发 | 行为 |
|------|------|------|
| 自动模式 | 用户选 0 / 历史策略编号 | 方案确认后全自动跑完，输出每步进度，不中途停下来 |
| 手动模式 | 用户选 M | 每步执行前停下来，让用户确认工具/轨道；确认后执行该步，再停下来 |

> **强制暂停例外**（任何模式下都必须暂停）：
> - prod SQL EXPLAIN 判定为危险
> - 需要使用外部库（JDBC / 非内部 adapter）
> - 空结果重试 3 次仍无结果

## 规划步骤

### ▶ Step 0：环境探查（必做，不可跳过）

1. 读取每个 adapter 的 `config.yaml`，确认 `enabled`、profiles、连接信息，并标注内部/外部类型
2. Platform adapter 额外探查：执行 `SHOW CATALOGS`，JDBC catalog 用三段式路径访问
3. 输出可用工具清单，**外部库明确标注**：

```
当前可用工具：
  sls            → prod, test, uat           [内部]
  mysql          → polardb-test, polardb-uat, main-test, main-uat  [内部]
  redis          → finance-test/uat, activity-test/uat, price-test/uat, redis2-test  [内部]
  elasticsearch  → test-finance（6.x）       [内部]
  platform       → prod（Doris JDBC）        [外部 ⚠️ 需用户确认]
```

4. 环境隔离原则：不同环境数据不能混查；每步必须标注环境/profile

✅ **Step 0 完成，继续 Step 1。**

### ▶ Step 2：三轨入轨声明（0号自动模式必做）

> 开始执行前，AI 必须先声明入轨方式，用户可以在此纠正方向，避免查了一半才发现跑偏。

**根据当前掌握的信息，从三种入轨方式中选一种：**

| 入轨方式 | 触发条件 | 第一步做什么 |
|---------|---------|------------|
| 🔵 代码先行 | 已知接口名 / 业务场景明确 / 有服务名 | 读接口代码 → 提取关键字/表名 → 带着发现查日志或DB |
| 🟡 日志先行 | 不知道接口，但有关键字（用户ID/订单号/交易号） | 宽关键字查日志 → 找到接口名/traceId → 读该接口代码 → 继续深查 |
| 🟢 数据先行 | 有明确异常数据表现，知道哪张表或哪个字段 | 关键字找相关表 → 看哪些接口写这张表 → 读代码分析逻辑 |

**声明格式（必须输出）：**

```
本次选择 [🔵代码先行 / 🟡日志先行 / 🟢数据先行]
原因：___
第一步将：___
```

> 用户可在此纠正入轨方式，确认后再执行。

---

### ▶ Step 3：三轨协作执行（核心）

> 三轨不是串行切换，而是**交织推进**——任何一轨有新发现，立刻带入最相关的另一轨。

**每一步查完后，必须问自己：**

| 自检问题 | 有发现时的操作 |
|---------|--------------|
| 日志指向代码了吗？ | 有 traceId / 接口名 / 类名 → 立刻去读对应代码 |
| 代码指向数据了吗？ | 有表名 / Redis key / ES index → 立刻去查对应数据 |
| 数据指向日志了吗？ | 有时间戳 / 操作记录 → 立刻缩小日志时间窗重查 |

**禁止行为：**

| ❌ 禁止 | ✅ 正确 |
|--------|--------|
| 某一轨查不到就埋头继续查同一轨 | 查不到时带着已有线索跳到另一轨 |
| 日志查完再读代码，代码读完再查数据（顺序割裂） | 日志里出现接口名 → 立刻去读代码，不等日志查完 |
| 空结果直接报告「没查到」 | 空结果 → 换条件 / 换工具 / 换时间窗，最多重试3次 |

---

### ▶ Step 4：按需选择 Adapter（内部优先）

> 优先选内部 adapter；外部库须输出确认提示，等用户确认后才能使用。

**优先级：**

```
内部 adapter（mysql / sls / redis / es）> platform（外部 JDBC，需确认）> 其他外部方式（禁止）
```

**外部库确认格式：**

```
⚠️ 当前步骤建议使用外部库：platform（Doris JDBC）
原因：内部 adapter 不覆盖该数据源（仅 prod 分析数据）
**[确认使用]** **[换内部方案]** **[跳过此步]**
```

| Adapter | 适用场景 | 类型 |
|---------|---------|------|
| sls | 查日志、拉链路、提取 traceId | 内部 |
| mysql | 查业务记录（支付、订单、用户、钱包） | 内部 |
| redis | 查缓存状态、验证缓存一致性 | 内部 |
| platform (Doris) | 查统计数据、宽表 | 外部（需确认） |
| elasticsearch | 补充全文检索 | 内部 |

---

### ▶ Step 5：SQL 安全门控（prod 环境）

> prod 环境所有 SQL 在执行前必须先运行 EXPLAIN，自动判断是否危险。

**执行流程：**

```
1. 先执行 EXPLAIN <原始SQL>
2. AI 分析 EXPLAIN 结果，判断是否触发危险条件：
   - type = ALL（全表扫描）
   - rows > 100万
   - key = NULL（未命中索引）
   - AI 综合判断有性能风险
3a. 安全 → 输出「✅ EXPLAIN 通过（type=range, rows≈1200, key=idx_user_id），执行中…」→ 自动执行
3b. 危险 → 输出危险报告 → 暂停等待用户确认
```

**危险报告格式：**

```
⚠️ EXPLAIN 检测到风险
- 危险原因：全表扫描（type=ALL）/ 扫描行数 120万 / 未命中索引
- 涉及表：t_user_wallet
- 原始 SQL：
  SELECT * FROM t_user_wallet WHERE status = 1

建议优化：可考虑在 status 字段加索引，或增加 user_id 条件缩小范围

**[确认执行]** **[放弃]** **[我来改写 SQL]**
```

> test / uat 环境：跳过 EXPLAIN 流程，直接执行。

---

### ▶ Step 6：手动模式逐步确认

> 仅手动模式（M）生效；自动模式跳过本节，直接执行。

**每步停下来输出：**

```
⏸ 下一步（Step N / N+1）
- 目的：___
- 建议工具/轨道：___ [内部/外部]（原因：___）
- 备选：___

**[确认]** **[换工具：___]** **[换轨道：___]** **[停止]**
```

**确认后：**
1. 执行该步（若涉及 prod SQL 仍走 EXPLAIN 流程）
2. 输出该步结果摘要
3. 自动呈现下一步确认提示

---

### ▶ Step 7：方案规划与收敛判断

> 单线推进，按证据驱动逐步执行。

**步骤五要素（缺一不可）：**

| 要素 | 含义 | 禁止写法 |
|------|------|---------|
| 目的 | 这一步要澄清什么 | 「查一下数据库」 |
| 工具 | adapter 名 + 内部/外部 | 「查库」（未指明） |
| 环境 | profile 名 | 「线上」（未映射） |
| 查什么 | 关键字、表/字段、key 模式 | 「看日志」 |
| 预期 | 看到什么算有价值 | 缺失 |

**收敛判断：**

| 状态 | 操作 |
|------|------|
| 三轨互相印证 | 给出结论，进入 result-analysis.md |
| 某轨缺失但其他两轨已闭环 | 标注「⚠️ 未证实」给弱结论 |
| 三轨都没线索 | 停下来告知用户，请求补充信息 |

---

### ▶ Step 8：检查通用决策

读取 `memory/confirmations.yaml`，跳过已决策项（如默认 prod 环境）。

✅ **规划完成，等待用户确认后开始执行查询。**

## 格式规则

1. 方案头部必须有摘要卡片，含入轨方式和执行模式
2. 入轨声明必须在步骤表格前单独输出
3. 工具列必须标注内部/外部
4. 执行进度表加「下一步」列，体现三轨流转；prod SQL 标注 EXPLAIN 结果
5. 手动模式每步必须有备选方案供用户选择
6. 选项必须用加粗方括号 `**[选项]**`
7. 不要大段纯文本，超过 3 行转表格或列表

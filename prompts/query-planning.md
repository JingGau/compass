# 查询规划

**职责**：根据实体、场景和代码理解，制定具体的查询方案，展示给用户确认。

## 执行前硬约束（与 SKILL.md「首轮回复门禁」一致）

1. **在用户对查询方案明确确认之前，禁止调用任何 adapter**（含在终端执行 `python adapters/.../client.py`、禁止偷偷跑 SQL）。
2. **策略不是固定流程**：每次规划前必须读取 `memory/strategies.yaml` 做匹配；有命中则展示 Top 3 及理由；无命中则从零写 plan，并写清「为何先查这一步」。
3. **禁止「第一步没数据就结束」**：任一步空结果/失败时，自动切换替代路径（改关键字、改时间、改 logstore/表、换环境、换工具），无需中断用户，直到得出结论或耗尽路径。
4. **环境探查（0.5）不得跳过**：未读各 adapter `config.yaml` 前，不得假设某工具在该环境可用。
5. **执行查询默认只用罗盘内 adapter**：通过 `adapters/<name>/client.py` 调用；不默认启用工作区其他 MCP 或绕过 adapter 的 CLI。见 `SKILL.md`「默认工具边界」。

## 执行模型：首次确认后全流程自动

**核心原则：用户确认方案后自动执行到底，但用户明确说「等等」「停」→ 立即中断。**

1. **首次确认**：展示方案后，等待用户确认
   - 用户明确说「好」「可以」「确认」「开始」→ 确认，开始执行
   - 用户意图不明确（含糊回应、不置可否）→ **默认走 0 号自动模式，直接开始**
   - 用户明确说「等等」「停」「等一下」「先别查」→ **立即中断，等待用户指示**
2. **自动执行**：确认后按方案逐步执行所有查询，每步完成后直接进入下一步，**不中途等待用户**
3. **自动容错**：任一步空结果/报错 → 自动尝试替代路径（换关键字、换时间窗、换 adapter），直到有数据
4. **仅在以下情况停下来告诉用户**：
   - 得出结论（展示结论卡片 + 证据链）
   - 所有路径都跑完仍无结论（告知现状，请用户补充信息或换方向）
   - 需要切到完全不同的策略方向（当前策略证据不足，需用户决策）
5. **执行中用户明确中断**：用户说「等等」「停」「先停一下」→ **立即停止当前查询**，保留已有结果，等待用户下一步指示
6. **执行中用户发了其他问题**：先回答用户问题，然后继续自动流程

## 用户角色适配

在展示方案前，判断当前用户角色（从会话上下文推断）：

| 角色 | 方案展示方式 |
|------|------------|
| **技术用户** | 完整步骤表格（含工具名、SQL、环境） |
| **业务用户** | 简化列表：「第1步查缓存、第2步查数据库、第3步查日志」 |

下方展示格式模板提供了两套样式，根据角色选择使用。

## 规划步骤

### 0. 代码理解（排查前置）

在制定查询方案前，先获取代码层面的理解：

**检查 `projects/` 目录**：
- 列出 `projects/` 下除 `_convention.md` 以外的 `.md` 文件
- 如果为空 → 跳过此步骤，直接进入步骤 1（降级模式）

**识别涉及的服务**：
- 从用户描述和场景分类结果推断涉及的后端服务
- 读取对应的 `projects/<service>.md`

**B 端问题追溯链**：
1. 先读 `projects/omp-shop.md`（如果存在）→ 匹配用户提到的页面/功能
2. 从"API 调用"表找到对应后端接口和服务名
3. 跳转到 `projects/<service>.md` → 找到"排查路径"表中的入口代码
4. **读入口代码的实际文件**（Controller → Service），理解：
   - 业务逻辑流程（先查缓存还是先查 DB？）
   - 涉及哪些表、Redis key
   - 可能抛出的异常和错误条件
   - 日志中会打印的关键字

**C 端问题**：
1. 从实体类型推断涉及的服务（订单 → order_server，支付 → finance_server）
2. 读 `projects/<service>.md` → 找"排查路径"中匹配的问题入口
3. 读入口代码理解逻辑

**知识缺口记录**：
- 如果需要的服务在 `projects/` 中没有对应文件 → 记录到会话的「知识缺口」列表
- 排查结束后提示用户注册（见 `strategy-improvement.md`）

### 0.5 环境探查（规划前必做）

在规划任何查询之前，**必须先检查当前可用的工具和环境**，不能凭假设规划。

**探查步骤**：

1. **读取每个 adapter 的 `config.yaml`**，确认：
   - `enabled` 是否为 `true`（关闭的 adapter 不可用）
   - 有哪些 `profiles`（每个 profile 对应一个环境/实例）
   - 每个 profile 的连接信息是否完整

2. **建立当前可用工具清单**：

```
当前可用工具：
  platform       → prod（仅线上，无测试环境）
  sls            → prod, test, uat
  mysql          → polardb-test(yunkc_finance), polardb-uat(yunkc_finance), main-test(yunkc_base), main-uat(yunkc_base)
  redis          → finance-test(db30), finance-uat(db30), activity-test(db10), activity-uat(db10), price-test(db10), price-uat(db12), redis2-test(db0)
  elasticsearch  → test-finance（6.x，仅测试环境）
```

3. **环境隔离原则**：
   - **不同环境的数据不能混查**：不能用 prod 的日志关联 test 的数据库
   - **platform 只有 prod**：如果问题发生在测试环境，不能用 platform 查
   - **确定目标环境**：从用户描述或 `memory/confirmations.yaml` 确定排查环境
   - **查询方案中必须标注每步的环境/profile**

4. **工具不可用时的处理**：
   - adapter `enabled: false` → 跳过，不纳入方案
   - 目标环境下无对应 profile → 告知用户该环境不可用
   - 连接信息不完整 → 告知用户需补充配置

**展示格式**（方案中标注环境）：

```
Step 1 [sls → prod] 查支付日志
Step 2 [mysql → polardb-test] 查支付记录
Step 3 [redis → finance-test] 查缓存状态
```

### 1. 匹配历史策略

读取 `memory/strategies.yaml`，对 `strategies` + `presets` 列表中的每条策略进行多维度评分。

**1.1 评分公式**

```
总分 = W_cat × 类别匹配度
     + W_kw  × 关键字命中率
     + W_ent × 实体类型覆盖度
     + W_svc × 服务匹配度
     + W_eff × effectiveness
     + W_rec × 时间衰减因子
```

各权重 `W_*` 从 `strategies.yaml` 的 `matching_weights` 配置读取：
- `category` (0.30)：问题分类完全匹配 = 1.0，同大类 = 0.5，不匹配 = 0
- `keywords` (0.20)：`命中关键词数 / 策略关键词总数`
- `entity_types` (0.10)：`当前可用实体类型 ∩ 策略所需实体类型 / 策略所需实体类型`
- `services` (0.15)：`当前涉及服务 ∩ 策略服务 / 策略服务`
- `effectiveness` (0.15)：直接取策略的 `score.effectiveness`
- `recency` (0.10)：`max(0, 1 - 天数差/180)`，从未使用的 preset 取 0.5

**1.2 展示与选择**

按总分降序排列，展示 Top 3（总分 >= 0.4 的策略），**并在首位添加 0 号自动模式**：

```
排查方案选择：

  ⭐ 0 | 自动模式（推荐，默认）
       证据优先，不假设根因，按实际数据走：
       先查日志（SLS）→ 读代码定位 → 必要时查数据表（Doris/MySQL）
       每一步根据上一步的证据决定下一步查什么，杜绝猜测

  1 | 策略「钱包-余额异常」（匹配度 94%，用过 14 次，成功率 92%）
      Redis缓存 → DB对比 → 操作日志

  2 | 策略「钱包-充值未到账」（匹配度 78%，用过 6 次，成功率 83%）
      支付回调日志 → 资金流水

  3 | 策略「账户冻结异常」（匹配度 65%，用过 3 次，成功率 67%）
      冻结记录 → 缓存状态

  4 | 我有自己的想法（输入你的排查思路）

> 输入编号选择，或直接回车/说「好」→ 默认执行 **0 号自动模式**
> 选择 0-3：**[0]** **[1]** **[2]** **[3]** **[4：自定义]**
```

**选择规则**：
- 用户明确选 `0`/`自动`/`默认` → **0 号自动模式**
- 用户明确选 `1`/`2`/`3` → 对应历史策略
- 用户明确选 `4` 或描述了自己的排查想法 → 按用户思路规划
- **用户意图不明确**（含糊回应、不置可否、没说清楚选哪个）→ **默认走 0 号**
- 用户明确说「好」「可以」「确认」「开始」→ 视为确认当前展示的方案（含默认 0 号）
- **用户明确说「等等」「停」「等一下」「先别查」→ 立即中断，等待用户指示**

**0 号自动模式的执行原则**：
1. **资源自由组合**：记忆库（strategies）、知识库（knowledge）、代码库（projects）、各 adapter 可根据需要随时调用，不限固定路径
2. **第一步默认 SLS**：从日志入手获取第一手证据，提取线索（traceId、关键字、时间点、异常信息）
3. **证据驱动**：每一步的查询条件和方向由上一步的实际返回决定，不预假设根因
4. **可重复调用**：同一 adapter 可多次调用（如先查一轮日志锁定时间，再缩小范围查一轮），不受"用过一次就不查"限制
5. **杜绝假设**：不在无证据的情况下推断根因并据此规划后续步骤——**每一步都必须有上一步的证据支撑**
6. **自动容错**：空结果自动换条件重查，不中断用户

**1.3 策略复用与验证**

- 用户选择策略 → 将策略的 `plan` 作为基础方案
- 替换模板中的 `{entity}` 占位符为当前实体值
- **环境验证**：检查策略中每个 step 的 adapter 在当前目标环境下是否可用
  - 不可用的 step → 自动标记跳过，告知用户原因
  - 例：策略用了 `platform` 但当前排查的是测试环境 → 跳过该步骤
- 如果有代码理解结果，验证策略的查询模板是否仍然有效（表名/key 有没有变）
- 用户可以在确认前微调步骤（增删改步骤）
- 微调会在归档时记录到 `modification_count`

**1.4 无匹配时**

所有策略评分 < 0.4 → 跳过策略匹配，从零规划（进入 Step 2 选择 Adapter）。

### 2. 按需选择 Adapter（不是全都用）

**核心原则：只选择解决问题所需的最少工具，不是把所有 adapter 都用上。**

选择时结合两个输入：
- Step 0.5 的环境探查结果（哪些工具在目标环境下可用）
- Step 0 的代码理解结果（代码逻辑涉及了什么）

**有代码理解时**（精准选择）：
- 代码中有 Redis 读取 → `redis`（仅当目标环境有 redis profile）
- 代码中有 DB 查询 → `mysql` 或 `platform`（platform 仅 prod 可用）
- 代码中有日志打印 → `sls`（用代码中提取的关键字）
- 代码中有 ES 查询 → `elasticsearch`
- 代码中没涉及的数据源 → **不选**

**无代码理解时**（降级选择，仍需克制）：
- 从问题描述推断最可能涉及的 1-3 个 adapter
- 不要"以防万一"把所有 adapter 都加上

**环境约束**（硬性）：
- `platform` → 只有 prod，测试环境问题不用它
- `sls` → 确认目标环境（prod/test/uat）的 project 和 logstore 名
- `mysql` → 确认目标环境对应的 profile（不同库不同 profile）
- `redis` → 确认 standalone 还是 cluster，哪个 profile
- `elasticsearch` → 确认版本和 profile

**每步标注环境**：查询方案中的每个步骤必须标注使用的 adapter + 环境/profile。

### 3. 多方案规划

当问题可能涉及多个链路或原因时，**不要只规划一条路径**，而是列出所有合理的排查方向作为独立方案。

#### 3.1 何时必须出「多个方案」让用户选（强制）

满足 **任一** 即不得只给单方案：

| 触发条件 | 做法 |
|---------|------|
| 用户一次提供 **≥2 类独立实体**（如同时有订单号 + 充值流水号 + 机构 ID，且可能对应不同根因） | 每类线索一条 **方案 A/B**，表头写清「本方案优先回答的疑问」 |
| 用户描述 **≥2 个独立症状** 或「既…又…」「两个都有问题」 | 按症状拆方案，或按链路拆方案，**不得**混成一步「综合查」却不列子目标 |
| 策略匹配 **Top1 与 Top2 分差小于 10%**（或两策略类别不同但都可能对） | **并列**两方案，请用户选 A / B |
| C端 / B端 **判断不确定** 且两条路径查询差异大 | **方案 A（按 C 端）** vs **方案 B（按 B 端）**，并追问一句缩小范围 |
| 用户明确说「不确定是 A 还是 B」 | 必须 **A / B 两方案**，每方案首行写「若根因是 A…」「若根因是 B…」 |

**展示要求**：先给一张 **方案对照总表**（| 方案 | 要回答的核心问题 | 主要工具 | 依赖实体 |），再展开各方案步骤表。选项格式：**`[执行 A]` `[执行 B]`**。

#### 3.2 单方案时步骤也必须「五要素」

即便只有一个方案，**每一步**也必须写全，禁止模糊话术：

| 要素 | 含义 | 反面示例（禁止） |
|------|------|------------------|
| **目的** | 这一步要澄清什么判断 | 「查一下数据库」 |
| **工具** | 罗盘 adapter 名：`sls` / `mysql` / `redis` / `elasticsearch` / `platform` | 「查库」（未指明） |
| **环境** | `prod` / `test` + profile 名 | 「线上」（未映射到 profile） |
| **查什么** | 关键字、表/字段意图、key 模式（技术用户可给示例 SQL） | 「看日志」 |
| **预期** | 看到什么算「这一步有价值」 | （缺失） |

**方案依赖分析**：
- 级联方案（B 依赖 A 的结果）→ 标记依赖，按顺序串行执行
- 交叉方案（共享部分查询）→ 提取公共查询，避免重复执行

### 4. 检查通用决策

读取 `memory/confirmations.yaml`，跳过已决策项（如「默认 prod 环境」）。

### 三、单方案展示（方向明确时）

步骤表须含 **目的** 列（或与「操作」合并为「目的+操作」），避免含糊：

```markdown
#### 排查方案

| Step | 目的（澄清什么） | 工具(adapter) | 环境/profile | 操作与查询内容 | 预期现象 |
|------|-----------------|---------------|-------------|----------------|---------|
| 1 | 确认缓存是否与 DB 一致 | redis | test | `GET wallet:balance:789:123456` | 拿到缓存数值或 key 不存在 |
| 2 | 确认 DB 权威余额 | mysql | polardb-test | `SELECT available_amount FROM t_user_wallet WHERE user_id=123456 AND org_id=789` | 一行结果 |
| 3 | 查是否有异常扣减/调账 | sls | prod | `walletOperate AND 123456`，最近 24h | ERROR 或关键 info |

> **代码依据**：`WalletServiceImpl` 先读 Redis(`wallet:balance:{orgId}:{userId}`)，未命中再查 `t_user_wallet` 表
>
> 确认后自动执行全部步骤，中途不打断。 **[确认开始]** / **[调整步骤]** / 直接回车默认执行
```

### 四、多方案展示（多条排查链路时）

**务必**先给总览对照（用户一眼能选），再展开子表：

```markdown
#### 排查方案（选择一个方向执行）

| 方案 | 优先回答的核心问题 | 主要 adapter | 依赖实体 |
|------|-------------------|-------------|---------|
| A | 支付回调是否成功、支付单状态 | sls + mysql | trade_seq |
| B | 订单生命周期是否卡状态 | sls + platform | order_id |
| C | 账户资金是否异常变动 | mysql + redis | user_id, org_id |

---

**方案 A — 支付链路排查**（适用：用户关心扣款/回调/支付单）

| Step | 目的 | 工具 | 环境 | 操作 | 查询内容 | 预期 |
|------|------|------|------|------|---------|------|
| A1 | 是否有回调错误 | sls | prod | 搜支付回调日志 | `payNotify AND {tradeSeq}` | 见 ERROR 或成功轨迹 |
| A2 | 支付单库表状态 | mysql | polardb-test | 查支付记录 | `SELECT * FROM t_payment_record WHERE trade_seq='{tradeSeq}'` | 一行明确状态 |

---

**方案 B — 订单链路排查**（适用：用户关心订单进度/充电记录）

| Step | 目的 | 工具 | 环境 | 操作 | 查询内容 | 预期 |
```

### 格式规则

1. **方案头部**：必须有问题摘要卡片（引用块 + 小表格）
2. **查询步骤**：技术用户用完整表格（`Step | 工具 | 环境 | 操作 | 查询内容`），业务用户用简化表格（`步骤 | 做什么 | 预计耗时`）
3. **代码依据**：技术用户展示（引用块），业务用户隐藏
4. **用户选项**：必须用加粗方括号 `**[选项]**` 格式，便于快速定位
5. **多方案分隔**：每个方案间用 `---` 分隔，方案名加粗
6. **不要大段纯文本**：任何超过 3 行的信息都应转为表格或列表
7. **业务用户禁止展示**：SQL 语句、Redis 命令、代码类名/方法名、adapter 名称

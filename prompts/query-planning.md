# 查询规划

**职责**：根据实体、场景，制定具体的查询方案，展示给用户确认。

## 执行前硬约束（与 SKILL.md「首轮回复门禁」一致）

1. **在用户对查询方案明确确认之前，禁止调用任何 adapter**。
2. **策略匹配**：每次规划前读 `memory/strategies.yaml` 做匹配；有命中展示 Top 3；无命中从零写 plan。
3. **禁止「第一步没数据就结束」**：空结果/失败时自动切换替代路径（改关键字、改时间、改 logstore/表、换环境、换工具）。
4. **环境探查（0.5）不得跳过**：未读各 adapter `config.yaml` 前，不得假设某工具在该环境可用。
5. **使用 MCP 工具**：直接调用 MCP 工具（`mcp__sls-client__*`、`mcp__mysql-client__*` 等），不通过 Bash 跑 Python 调用 adapter。

## 执行模型：首次确认后全流程自动

**核心原则：用户确认方案后自动执行到底，但用户明确说「等等」「停」→ 立即中断。**

1. **首次确认**：展示方案后等待用户确认
   - 用户说「好」「可以」「确认」「开始」→ 开始执行
   - 用户意图不明确 → **默认走 0 号自动模式，直接开始**
   - 用户说「等等」「停」「等一下」「先别查」→ **立即中断**
2. **自动执行**：确认后按方案逐步执行，**不中途等待用户**
3. **自动容错**：空结果 → 自动换条件重查，不中断
4. **停下来告诉用户**：得出结论 / 所有路径耗尽仍无结论 / 需切换完全不同的策略方向
5. **执行中用户中断**：立即停止，保留已有结果
6. **执行中用户发其他问题**：先回答，再继续自动流程

## 用户角色适配

| 角色 | 方案展示方式 |
|------|------------|
| **技术用户** | 完整步骤表格（含工具名、SQL、环境） |
| **业务用户** | 简化列表：「第1步查缓存、第2步查数据库、第3步查日志」 |

## 规划步骤

### 0. 环境探查（规划前必做）

**必须先检查当前可用的工具和环境，不能凭假设规划。**

1. **读取每个 adapter 的 `config.yaml`**，确认 `enabled`、profiles、连接信息
2. **Platform adapter 额外探查（Doris）**：
   - 必须执行 `SHOW CATALOGS` 获取所有 catalog（internal + jdbc）
   - `SHOW DATABASES` 只返回 internal catalog 的库，JDBC catalog 用三段式路径
3. **建立当前可用工具清单**：

```
当前可用工具：
  platform       → prod（仅线上，无测试环境）
  sls            → prod, test, uat
  mysql          → polardb-test(yunkc_finance), polardb-uat(yunkc_finance), main-test(yunkc_base), main-uat(yunkc_base)
  redis          → finance-test(db30), finance-uat(db30), activity-test(db10), activity-uat(db10), price-test(db10), price-uat(db12), redis2-test(db0)
  elasticsearch  → test-finance（6.x，仅测试环境）
```

4. **环境隔离原则**：
   - 不同环境数据不能混查
   - platform 只有 prod
   - 每步必须标注环境/profile

### 1. 匹配历史策略

读取 `memory/strategies.yaml`，按多维度评分排序，展示 Top 3 并加入 0 号自动模式：

```
排查方案选择：

  ⭐ 0 | 自动模式（推荐，默认）
       资源自由组合，证据驱动，不假设根因
       每一步根据上一步的证据决定下一步查什么

  1 | 策略「钱包-余额异常」（匹配度 94%）
      Redis缓存 → DB对比 → 操作日志

  2 | 策略「充值未到账」（匹配度 78%）
      支付回调日志 → 资金流水

> 输入编号选择，或直接回车/说「好」→ 默认执行 **0 号自动模式**
```

**0 号自动模式的执行原则**：

```
1. 代码嵌入查询，不做独立前置
   - 查什么之前读什么代码，不用先全读一遍
   - 代码的价值是缩小范围：哪个容器、哪个接口、哪个关键字

2. 查日志优先链路追踪法
   - 先用宽关键字探路，拿到日志
   - 从日志中提取 traceId / tlogid / 线程ID
   - 用链路 ID + 小时间窗口，一次性拉完整链路
   - 再基于链路上下文，针对关键节点精查

3. 代码缩小范围，查不到时逐步放宽
   - 先用代码确认的条件查（SLS 用代码里的容器名、接口名过滤）
   - 查不到 → 逐步去掉代码加的条件（去掉容器、去掉接口）
   - 只保留核心关键字（traceId / trade_seq）
   - 重新查，避免条件锁死导致漏掉

4. 日志 → 代码 → 数据，迭代循环
   - 日志不够 → 读代码找新关键字或链路 ID
   - 缺少参数 → 查数据库表（拿 user_id、trade_seq 等）
   - 再用新发现去查日志，不断迭代缩小范围
```

### 2. 按需选择 Adapter

**核心原则：只选解决问题所需的工具，不是全部用上。**

- SLS：查日志、拉链路
- MySQL：查业务记录（支付、订单、用户）
- Redis：查缓存状态
- Platform (Doris)：查统计数据、宽表
- Elasticsearch：补充全文检索

**结合代码理解选择**：
- 代码中有日志打印 → `sls`
- 代码中有 DB 查询 → `mysql` 或 `platform`
- 代码中有 Redis → `redis`
- 代码中没有涉及的数据源 → **不选**

### 3. 路径解析（代码定位规则）

**路径解析规则**：
1. 读 `config/code-repos.yaml`，解析 `code_root`（从 `.env` 读取 `${CODE_ROOT:-...}`）
2. 项目在 `projects` 映射 → `code_root` + 相对路径
3. 项目不在映射 → 在 `code_root` 下递归扫描同名子目录
4. `projects/*.md` 中的 `代码根路径` 是相对路径

**代码嵌入时机**：
- 查 SLS 前 → 读代码确认关键字、容器名、traceId 生成位置
- 查 MySQL/Platform 前 → 读代码找涉及的表名、字段
- 查 Redis 前 → 读代码找 key 模式

### 4. 多方案规划

当问题可能涉及多个链路或原因时，**列出所有合理的排查方向**。

#### 必须出多方案的场景

| 触发条件 | 做法 |
|---------|------|
| 用户一次提供 ≥2 类独立实体 | 每类线索一条方案 |
| 用户描述 ≥2 个独立症状 | 按症状/链路拆方案 |
| Top1 与 Top2 分差 < 10% | 并列两方案 |
| C端 / B端 判断不确定 | 方案 A（B端） vs 方案 B（C端） |

**展示要求**：先给方案对照总表，再展开各方案步骤。

#### 单方案步骤五要素

| 要素 | 含义 | 禁止 |
|------|------|------|
| **目的** | 这一步要澄清什么 | 「查一下数据库」 |
| **工具** | adapter 名 | 「查库」（未指明） |
| **环境** | profile 名 | 「线上」（未映射） |
| **查什么** | 关键字、表/字段、key 模式 | 「看日志」 |
| **预期** | 看到什么算有价值 | 缺失 |

### 5. 检查通用决策

读取 `memory/confirmations.yaml`，跳过已决策项（如默认 prod 环境）。

## 格式规则

1. 方案头部必须有摘要卡片
2. 技术用户用完整表格，业务用户用简化表格
3. 业务用户禁止展示：SQL、Redis 命令、adapter 名称、代码类名
4. 选项目须用加粗方括号 `**[选项]**`
5. 多方案间用 `---` 分隔
6. 不要大段纯文本，超过 3 行转表格或列表

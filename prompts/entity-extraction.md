# Problem Intake 与实体提取

**职责**：从用户自然语言描述中识别可用于查询的结构化实体，并把混乱输入整理成可执行排查工单。

> **本阶段只产出实体清单，禁止执行任何 adapter 或数据库/日志查询。** 完整分析与方案见后续步骤与 `query-planning.md`。

## Intake 必做项

1. 保留用户原始问题摘要。
2. 用一句话改写为标准化问题。
3. 判断影响范围：单用户 / 多用户 / 单订单 / 批量 / 未知。
4. 识别实体并标注来源文本、置信度。
5. 判断是否缺少最小定位实体；缺失时先追问，不进入查询规划。

## 需要识别的实体

| 实体类型 | 识别特征 | 说明 |
|---------|---------|------|
| `user_phone` | 11位数字，1开头 | 用户手机号 |
| `user_id` | 纯数字 ID，上下文明显是用户 | 用户唯一标识 |
| `user_name` | 用户昵称/姓名 | 用户名称 |
| `record_id` | 纯数字，上下文是订单/充电记录 | 订单或充电记录 ID |
| `trade_seq` | 长串数字，通常 30+ 位 | 支付交易流水号 |
| `pay_no` / `pay_inside_no` | 支付单号、商户订单号 | 财务支付单 |
| `clear_no` | 清分单号、分账单号 | 财务清分单 |
| `merchant_id` | 商户号、商户 ID | 支付/账户映射 |
| `refund_no` | 退款单号、垫资单号 | 退款/垫资链路 |
| `gun_id` | 枪号，通常 5 位数字 | 充电桩枪号 |
| `station_id` / `station_name` | 电站 ID 或名称 | 充电站标识 |
| `org_id` / `org_name` | 机构/车队 ID 或名称 | 机构/车队标识 |
| `time_range` | 时间描述（今天/昨天/3月15日/最近1小时） | 问题发生时间范围 |
| `dt_month` | 从 time_range 中推断，格式 `YYYY-MM-01` | 按月分区月份 |

## 输出格式

```
原始问题：用户说今天下午充电失败，怀疑支付没回调
标准化问题：排查某用户今天下午充电失败是否由支付回调异常导致
影响范围：单用户（待验证）

识别到的实体：
| 实体 | 值 | 来源 | 置信度 |
|------|----|------|--------|
| time_range | 今天下午 | “今天下午” | 中 |

缺失实体：
| 缺失项 | 是否阻断 | 可替代信息 | 追问 |
|--------|----------|------------|------|
| user_id/手机号/订单号 | 是 | 任一即可 | 请补充用户ID、手机号或订单号 |
```

## 特殊处理

- **无时间信息**：不得默默默认最近 24 小时；若用户允许，可建议「最近 30 分钟 / 1 小时 / 当天」让用户确认
- **多个 ID**：全部保留在实体池，查询时逐个使用
- **模糊实体**（如"那个用户"）：询问用户澄清，或从会话历史中推断
- **缺少最小定位实体**：必须暂停追问，不调用 adapter

## 冲突实体处理

当用户描述中出现同类型的多个实体时，按以下规则处理：

| 冲突场景 | 处理规则 |
|---------|---------|
| 多个手机号 | 全部保留，标注为 `user_phone_1`、`user_phone_2`，询问用户「要查哪个用户？还是都查？」 |
| 多个订单号 | 全部保留，标注为 `record_id_1`、`record_id_2`，在方案阶段对每个订单生成独立查询 |
| 手机号 + user_id 共存 | 先假设是同一个用户，标记 `待验证关联`，Step 4 查询时先验证一致性 |
| 多个时间范围矛盾 | 询问用户确认具体时间段（如「昨天下午」和「今天上午」哪个是问题发生时间） |
| 电站名 + 电站ID 共存 | 优先使用 station_id（精确），station_name 作为校验 |

**原则**：不默默丢弃任何实体，全部保留在实体池中。冲突的实体在查询规划阶段会被拆成多方案或在首步查询中做关联验证。

# 结果分析

**职责**：汇总三轨查询结果，输出带证据链的结构化结论，供用户理解根因、制定处置措施。

> 本文件被 SKILL.md Step 7 引用。输入来自 `query-planning.md` 三轨收敛后的状态卡，输出结论卡片 + 排查过程卡片（技术用户）。

---

## ⛔ 进入本文件前的前置检查

**以下两项必须满足，否则禁止输出结论，回到 query-planning.md 补充查询：**

1. `query-planning.md` 三轨状态卡已输出，且收敛判断不为「三轨均无线索」
2. 代码轨状态为 ✅完成 或 有明确的「情况B说明（无法触发的原因）」
3. Investigation State 中至少存在 1 条可引用证据
4. 根因结论引用了证据 ID；未引用证据的判断只能输出为「待验证假设」

> 若代码轨状态为❌未触发且无说明 → 禁止输出结论，返回补充。

## 🧠 输出结论前的【根因下钻五问】

> 这是输出 conclusion 的最后一道软门禁。每个问题必须在脑子里过一遍；
> 任何一问得出 "不知道" 或 "似乎不算根因"，就**回到查询轨补证据**，不要急着 conclude。

| # | 问题 | 通过标准（满足后才能继续） | 不通过怎么办 |
|---|------|--------------------------|--------------|
| 1 | 这是【现象】还是【根因】？把当前结论再问一次 "why"，能继续往下挖吗？ | 已经挖到 "代码逻辑/配置项/数据缺失/外部输入" 这一层，无法再用 "为什么会这样" 进一步追问 | 用 `compass action plan track=code` 或 `track=sql` 继续往下挖一层 |
| 2 | 为什么【之前】没出问题、【现在】才出？变化点是什么？ | 能给出一个具体的变化（变更/数据/流量/上游/灰度/依赖版本/时间窗口），且与故障窗口对得上 | 用 `compass change record` 登记疑似变更；用 `scene fact --category baseline/diff` 把"正常态 vs 异常态"写下来 |
| 3 | 这个根因能解释【全部异常案例】吗？还是只解释了样本中的一部分？ | 至少 2 个独立样本符合同一根因，或明确给出"为何只有部分案例命中"的边界条件 | 再补一两个样本走一遍；不能走通就把结论降为 "假设" 或拆成多个根因 |
| 4 | 同一根因还会影响哪些【相邻入口/数据/链路】？同类是不是也已经/即将出问题？ | 显式列出至少 1 个同类扫描方向（哪些数据/接口/用户群应该一起看） | 把同类扫描方向写进 `--pattern-scan` 字段；如果懒得扫请显式说明 "无同类影响" 的依据 |
| 5 | 如果【这个根因不存在】，问题还会发生吗？反证条件是什么？ | 能给出一个"如果 X 不发生，问题就不发生"的反证陈述（写进对应假设的 falsifiable 字段） | 用 `compass hypothesis add --falsifiable ...` 给关键假设补充反证条件；找一个反例样本验证 |

**没过五问的标志（任意 1 条命中就先别 conclude）**：

- 推断链是 "X → Y → 问题"，但说不清 "为什么 X 会发生"。
- 推断链是 "因为代码里有 bug"，但拿不出 git blame / 该代码近期变更点。
- 全部样本都来自同一个用户/订单/时间点（孤证）。
- 故障消失了但你也说不出 "为什么消失"（"自愈" 不是解释）。
- 结论里出现 "可能/也许/估计/应该是" 这类弱化词。

通过五问后，再按下文格式输出结论卡片。

> 五问中第 1、2、4 题与 `compass next` 触发的"根因反思三问"一一对应；
> 务必用 `compass reflect answer --question 1|2|3 --answer "..."` 把答案落盘，
> `report` 中会自动渲染问答对到「根因反思（自我盘问）」段，让评审看得见你思考过。

## 一、结论卡片

> **技术用户和业务用户都必须输出，但字段内容按角色适配。**

### 1.1 一句话结论（必填，20字以内）

```
🔴 根因：___
```

直接说技术根因，不说现象。例：
- ✅ `Redis 缓存穿透导致余额查询击穿到 DB，DB 数据尚未更新`
- ❌ `用户余额显示不正确`（这是现象不是根因）

若证据不足，不得输出“根因”，必须改为：

```
🟡 待验证假设：___
```

---

### 1.1.5 TL;DR + 严重等级 + MTTR（强烈推荐，决策者一眼看完）

> 给非技术决策者 / Oncall / 复盘评审使用。`report` 会自动用这段渲染头部 TL;DR 卡片
> 与 MTTD/MTTM/MTTR 时序表，因此最好通过 `conclude` 的对应参数落盘。

| 字段 | 命令参数 | 要求 |
|------|----------|------|
| TL;DR | `--tldr "<≤3 句>"` | 一段话讲清"故障是什么、影响多大、当前状态"。超 3 句会触发 `TLDR_TOO_LONG` 警告 |
| 严重等级 | `--severity sev1\|sev2\|sev3\|sev4` | 不传则按 blast_radius 启发式推荐；🔴 SEV1=资损/全站不可用，🟠 SEV2=核心功能受损，🟡 SEV3=部分用户/特定场景，🟢 SEV4=轻度异常 |
| 发现时间 | `--detected-at "<yyyy-mm-ddTHH:MM:SS+08:00>"` | 故障被监控/用户/oncall 发现的时间，默认 = `start_session` 时间 |
| 响应时间 | `--acknowledged-at "..."` | oncall 介入响应的时间；与 detected 之差 = MTTD |
| 止血时间 | `--mitigated-at "..."` | 止血动作生效、用户感知恢复的时间；与 acknowledged 之差 = MTTM |
| 解决时间 | `--resolved-at "..."` | 完全恢复、根治动作落地的时间；与 detected 之差 = MTTR |

如果 4 个时间戳缺失，不会阻塞 conclude，但报告里的时序表会显示 "—"，
评审时会被追问"为什么没记录响应时间"。

---

### 1.2 事件叙事（5W1H 框架，字段必填，不得留空）

| 维度 | 字段 | 说明 | 禁止写法 |
|------|------|------|---------|
| **What** | 发生了什么 | 具体的异常行为或状态变化，技术层面 | 「系统出错」「数据不对」 |
| **Where** | 哪个组件/调用链哪段 | 服务名 + 类名#方法名 + 调用链位置 | 「后端」「数据库」 |
| **When** | 何时 | 首次异常时间戳 + 持续时长（能确定则写，不能确定则写推断依据） | 「最近」「今天」 |
| **Why** | 根因（两层） | 技术根因（代码/配置/数据层面）+ 业务触发条件（什么操作触发了它） | 只说现象 |
| **Blast Radius** | 影响范围 | 影响了哪些用户/订单/数据，范围有多大（能量化则量化） | 「影响了部分用户」 |
| **How** | 传播链 | 问题如何从触发点扩散/放大到用户可感知的程度 | 缺失此字段 |

**输出格式：**

```markdown
## 🔍 排查结论

**🔴 根因**：Redis 缓存穿透 → 余额查询击穿到 DB → DB 数据未更新 → 余额展示为 0

| 维度 | 内容 |
|------|------|
| **What** | WalletServiceImpl.getBalance 查询 Redis key `wallet:123456` 返回 nil，fallback 查 DB 时 t_user_wallet.available_amount 仍为 0 |
| **Where** | finance-server · WalletServiceImpl#getBalance（调用链第 3 层） |
| **When** | 首次异常 2026-04-05 14:32:09；持续至 14:35:22（约 3 分钟），充值到账后自愈 |
| **Why — 技术根因** | Redis 缓存 TTL 在充值回调写入 DB 前 30 秒过期，导致穿透窗口期 |
| **Why — 业务触发** | 用户在充值回调处理期间（支付→到账约 2 分钟）立即刷新余额页面 |
| **Blast Radius** | 影响该用户单次查询；DB 查询量无异常放大（TTL 窗口极短）；无其他用户受影响 |
| **How（传播链）** | 用户充值 → 支付回调延迟 2min → 期间 Redis TTL 到期 → 用户刷新 → 穿透查 DB → DB 尚未更新 → 余额=0 |
```

## 二、证据链与可信度

> 技术用户必须输出；业务用户输出简化证据摘要。

### 2.1 输出格式

```markdown
## 🧷 证据链

**可信度**：高 / 中 / 低

| 证据ID | 来源 | 证据摘要 | 支持/排除 |
|--------|------|----------|-----------|
| E1 | SQL: xxx表 | 支付单状态为 SUCCESS | 支持 H1 |
| E2 | SLS: xxx服务 | 未检索到订单推进日志 | 支持 H1 |
| E3 | 代码: XxxService#method | 支付成功后应发送订单推进消息 | 支持 H1 |

**推断**：
E1 + E2 + E3 共同支持「支付成功事件未推进订单状态」。

**仍待验证**：
- MQ 是否发送失败或消费失败。
```

### 2.2 可信度规则

| 可信度 | 要求 |
|--------|------|
| 高 | 至少 2 类来源互相印证，如数据 + 日志、日志 + 代码 |
| 中 | 有直接证据，但缺少另一类来源交叉验证 |
| 低 | 只有间接线索或经验判断，必须标记为待验证 |

### 2.3 禁止写法

- 禁止：“应该是支付回调问题。”（无证据）
- 推荐：“待验证假设：支付回调未推进订单。已有证据 E1 显示支付成功，但缺少订单推进日志，需要继续查 MQ 消费。”

```markdown
关键链路：
页面 ___ → API ___ → Controller/Service ___ → 表 ___ → 数据状态 ___
```

若某条轨道没有证据，必须写明：
- 未覆盖轨道
- 已尝试的关键字/SQL/代码路径
- 为什么仍允许输出结论，或为什么只能输出弱结论

### 2.3 推断链（必填）

用一句话串联因果，**不允许分点列举，必须是连续的因果句**：

```markdown
### 推断链

用户于 14:32 充值 → 支付回调处理中（预计 14:34:18 写入 DB）→ 14:32:07 Redis TTL 恰好到期 → 用户 14:32:09 刷新余额 → WalletServiceImpl 查 Redis 返回 nil → fallback 查 DB → DB 此时 available_amount 仍为 0 → 余额展示为 0 → 14:34:18 DB 写入完成后下次查询自动恢复
```

> **禁止写法**：
> - ❌ 分点：「1. Redis过期 2. DB未更新 3. 展示为0」
> - ❌ 含糊：「因为缓存问题导致数据不一致」
> - ✅ 必须是有时间戳、有组件名、有数据值的完整因果句

## 格式规则

1. **结论卡片是必输出项**，技术/业务用户都要，内容按角色适配
2. **5W1H 字段全部必填**，不得留空，不得写「暂无」「待确认」
3. **推断链必须是连续因果句**，含时间戳 + 组件名 + 数据值，禁止分点
4. **Blast Radius 必须量化**，不得写「部分用户」「一些数据」
5. **完整排查流程必须输出在代码块中**，每步包含操作输入和输出，门控步骤不可省略
6. **原始证据默认折叠**，不主动展开
7. **业务用户隐藏**：完整排查流程、Where、Why技术根因、How、原始证据
8. 所有展示数据必须经过 `guards/data-masking.md` 脱敏处理

# 结果分析

**职责**：汇总三轨查询结果，输出结构化结论，供用户理解根因、制定处置措施。

> 本文件被 SKILL.md Step 7 引用。输入来自 `query-planning.md` 三轨收敛后的状态卡，输出结论卡片 + 排查过程卡片（技术用户）。

---

## ⛔ 进入本文件前的前置检查

**以下两项必须满足，否则禁止输出结论，回到 query-planning.md 补充查询：**

1. `query-planning.md` 三轨状态卡已输出，且收敛判断不为「三轨均无线索」
2. 代码轨状态为 ✅完成 或 有明确的「情况B说明（无法触发的原因）」

> 若代码轨状态为❌未触发且无说明 → 禁止输出结论，返回补充。

## 一、结论卡片

> **技术用户和业务用户都必须输出，但字段内容按角色适配。**

### 1.1 一句话结论（必填，20字以内）

```
🔴 根因：___
```

直接说技术根因，不说现象。例：
- ✅ `Redis 缓存穿透导致余额查询击穿到 DB，DB 数据尚未更新`
- ❌ `用户余额显示不正确`（这是现象不是根因）

---

### 1.2 事件叙事（5W1H 框架，字段必填，不得留空）

| 维度 | 字段 | 说明 | 禁止写法 |
|------|------|------|---------|
| **What** | 发生了什么 | 具体的异常行为或状态变化，技术层面 | 「系统出错」「数据不对」 |
| **Where** | 哪个组件/调用链哪段 | 服务名 + 类名#方法名 + 调用链位置 | 「后端」「数据库」 |
| **When** | 何时 | 首次异常时间戳 + 持续时长（能确定则写，不能确定则写推断依据） | 「最近」「今天」 |
| **Why** | 根因（两层） | 技术根因（代码/配置/数据层面）+ 业务触发条件（什么操作触发了它） | 只说现象 |
| **Blast Radius** | 影响范围 | 影响了哪些用户/订单/数据，范围有多大（能量化则量化） | 「影响了部分用户」 |
| **How** | 传播链 | 问题如何从触发点扩散/放大到用户可感知的程度 | 缺失此字段 |

**输出格式：**

```markdown
## 🔍 排查结论

**🔴 根因**：Redis 缓存穿透 → 余额查询击穿到 DB → DB 数据未更新 → 余额展示为 0

| 维度 | 内容 |
|------|------|
| **What** | WalletServiceImpl.getBalance 查询 Redis key `wallet:123456` 返回 nil，fallback 查 DB 时 t_user_wallet.available_amount 仍为 0 |
| **Where** | finance-server · WalletServiceImpl#getBalance（调用链第 3 层） |
| **When** | 首次异常 2026-04-05 14:32:09；持续至 14:35:22（约 3 分钟），充值到账后自愈 |
| **Why — 技术根因** | Redis 缓存 TTL 在充值回调写入 DB 前 30 秒过期，导致穿透窗口期 |
| **Why — 业务触发** | 用户在充值回调处理期间（支付→到账约 2 分钟）立即刷新余额页面 |
| **Blast Radius** | 影响该用户单次查询；DB 查询量无异常放大（TTL 窗口极短）；无其他用户受影响 |
| **How（传播链）** | 用户充值 → 支付回调延迟 2min → 期间 Redis TTL 到期 → 用户刷新 → 穿透查 DB → DB 尚未更新 → 余额=0 |
```

> 紧跟结论卡片输出，业务用户跳过此节。
>
> **目的**：排查过程跨越多条消息，Before/After Block 散落在各条消息中。这里将它们汇总成一个可复制的代码块，用户可直接复制作为排查报告。
>
> **数据来源**：直接从执行过程中已输出的 Before Block、Safety Gate Block、After Block 提取，不重新写。若某步信息缺失，标注 `（已省略）`。

### 2.2 推断链（必填）

用一句话串联因果，**不允许分点列举，必须是连续的因果句**：

```markdown
### 推断链

用户于 14:32 充值 → 支付回调处理中（预计 14:34:18 写入 DB）→ 14:32:07 Redis TTL 恰好到期 → 用户 14:32:09 刷新余额 → WalletServiceImpl 查 Redis 返回 nil → fallback 查 DB → DB 此时 available_amount 仍为 0 → 余额展示为 0 → 14:34:18 DB 写入完成后下次查询自动恢复
```

> **禁止写法**：
> - ❌ 分点：「1. Redis过期 2. DB未更新 3. 展示为0」
> - ❌ 含糊：「因为缓存问题导致数据不一致」
> - ✅ 必须是有时间戳、有组件名、有数据值的完整因果句

## 格式规则

1. **结论卡片是必输出项**，技术/业务用户都要，内容按角色适配
2. **5W1H 字段全部必填**，不得留空，不得写「暂无」「待确认」
3. **推断链必须是连续因果句**，含时间戳 + 组件名 + 数据值，禁止分点
4. **Blast Radius 必须量化**，不得写「部分用户」「一些数据」
5. **完整排查流程必须输出在代码块中**，每步包含操作输入和输出，门控步骤不可省略
6. **原始证据默认折叠**，不主动展开
7. **业务用户隐藏**：完整排查流程、Where、Why技术根因、How、原始证据
8. 所有展示数据必须经过 `guards/data-masking.md` 脱敏处理

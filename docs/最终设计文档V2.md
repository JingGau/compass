## 第一章：背景与目标

### 1.1 现状与痛点

云快充业务体系包含 30+ 微服务、覆盖 C端（用户 App）和 B端（omp-shop 商户管理后台）。线上问题排查面临以下困境：

**数据分散**：排查一个问题通常需要横跨 SLS 日志、Doris 数据仓库、甚至多个服务的代码，手动在多个系统间切换、拼接查询语句，效率极低。

**经验难沉淀**：每位开发者都有自己习惯的排查路径和关键字，新人面对同类问题需要从头摸索。排查经验散落在个人脑中，无法被团队复用。

**C端与B端割裂**：C端无前端代码，只能通过日志和数据反推用户行为；B端有完整的 omp-shop 前端，可以通过「页面 → 接口 → 日志」三层联动定位问题。两种排查路径完全不同，目前没有统一的方法论。

**安全性缺失**：直接在生产数据库上执行 SQL 没有任何防护，存在误执行高代价查询（全表扫描亿级数据）甚至误操作的风险。

### 1.2 目标

构建一个 OpenClaw Agent Skill，名为 `compass`（罗盘），实现：

| 目标 | 描述 |
|------|------|
| **自然语言驱动** | 用户用自然语言描述问题（含手机号、订单号、昵称等线索），AI 自动识别实体、规划查询 |
| **内置查询能力** | 通过 Python 脚本直接调用 SLS SDK、平台 HTTP、MySQL、Redis、Elasticsearch，不依赖外部 MCP |
| **安全门控** | SQL 三档 EXPLAIN 强卡、内部库优先、外部库确认、数据脱敏、审计日志 |
| **约定驱动扩展** | 未来新增 Nacos/MQ 等数据源时，AI 按约定自主创建 adapter，无损引入 |
| **自我进化** | 每次排查后自动归档策略，基于用户反馈调整策略权重，记忆越用越准 |
| **用户监督** | 所有关键决策（查询方案、prod SQL 执行、策略淘汰）必须经用户确认 |

### 1.3 成功标准

- 一个完整排查流程从用户描述到定位原因，平均交互轮次 ≤ 5 轮
- 新增一个 adapter 所需的人工操作 ≤ 1 句话描述 + 1 次确认
- 所有 prod SQL 100% 经过 EXPLAIN 三档强卡，0 条未经确认的写操作
- 排查策略库在使用 1 个月后可覆盖 80% 以上常见问题类型

## 第二章：架构设计

### 2.1 核心思想：约定驱动 + AI 作为运行时

传统软件中，"微内核 + 插件" 需要代码级的注册发现机制。但在 AI Skill 场景下，**AI 本身就是运行时**——它读文件、理解语义、做决策、执行操作。因此不需要传统的插件系统，而是采用「约定即契约」的思想：

- **约定** 替代接口定义：adapter 按固定目录结构和文件命名组织，AI 读取即理解
- **注册表** 是纯文本：SKILL.md 中维护一张 adapter 清单，AI 自己更新
- **扩展** 靠 AI 自身：新增能力时 AI 按约定创建文件，用户确认后生效

这种方式的根本优势是：**扩展能力不需要人写代码**，AI 按约定自主完成。

### 2.2 分层架构

```
┌──────────────────────────────────────────────────────────┐
│                    SKILL.md（总指挥）                      │
│  流程定义 · 能力注册表 · 安全规则引用 · 交互原则             │
│  （简洁稳定，职责清晰，细节全部引用子文件）                  │
└──────────────────────────┬───────────────────────────────┘
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │  Prompts │    │  Guards  │    │  Memory  │
    │ 提示词层  │    │ 安全门控 │    │  记忆层  │
    └──────────┘    └──────────┘    └──────────┘
          │                │                │
          │         ┌──────┴──────┐         │
          ▼         ▼             ▼         ▼
    ┌──────────────────────────────────────────┐
    │           Adapters（能力适配层）            │
    │  内部: SLS / MySQL / Redis / ES           │
    │  外部（需用户确认）: Platform（Doris JDBC） │
    └──────────────────────────────────────────┘
          │
          ▼
    ┌──────────────────────────────────────────┐
    │          Knowledge（知识层）               │
    │  系统拓扑 · B端页面 · 数据表 · 项目描述     │
    └──────────────────────────────────────────┘
```

### 2.3 各层职责

| 层 | 职责 | 修改频率 | 谁维护 |
|----|------|---------|--------|
| **SKILL.md** | 总调度入口。定义排查流程总览、能力注册表、安全规则引用、交互原则。**不含交互格式细节，细节在子文件** | 极低 | AI + 用户确认 |
| **Prompts** | 各阶段的执行规范。含交互格式、完成标志、禁止行为。`query-planning.md` 含三轨协作强制子流程 | 低 | AI 优化 + 用户审批 |
| **Guards** | 安全防线。`sql-safety.md` 是 EXPLAIN 三档的唯一权威来源，其他文件只引用 | 极低 | 用户配置 |
| **Memory** | 持久化记忆。查询策略、问题分类、用户决策、审计日志 | 高 | AI 自动写入 |
| **Adapters** | 外部数据源能力封装。内部 adapter 直接使用；platform（JDBC）需用户确认 | 中 | AI 创建 + 用户确认 |
| **Knowledge** | 业务知识。系统拓扑、页面-接口映射、数据表文档、项目描述 | 中 | AI 探索生成 + 用户确认 |

### 2.4 设计原则

**P1：用户始终拥有最终决策权**
所有涉及数据查询、知识写入、策略淘汰的操作，必须经过用户明确确认。AI 负责提案，用户负责审批。对于已经确认过的通用决策，记录后复用，不重复询问。

**P2：约定优于配置**
adapter 不需要注册声明文件（如 plugin.yaml），只要目录结构和文件命名符合约定，AI 就能识别和使用。

**P3：按需加载，不预读全部**
AI 在收到用户问题后，先判断需要哪些能力，再读取对应 adapter 的 README 和 knowledge。不在一开始就加载全部文件，节省 context window。

**P4：渐进式知识积累**
knowledge/ 和 memory/ 初始都为空。通过使用逐步积累，每一次排查都在为下一次铺路。但积累必须有边界——内置压缩和过时淘汰机制，防止信息膨胀。

**P5：无损扩展**
新增 adapter 时：① 新建独立目录 ② 更新 SKILL.md 注册表加一行。不修改任何已有文件的内部逻辑。

**P6：单一来源**
每类规则只在一个文件中定义。EXPLAIN 规则在 `guards/sql-safety.md`，临时文件规则在 `guards/temp-files.yaml`，其他文件只做引用，不重复定义。

## 第四章：SKILL.md 设计

### 4.1 SKILL.md 的四大职责

**① 能力注册表**（含类型标注）

```
| Adapter       | 用途                | 环境覆盖         | 类型           | 状态  |
|---------------|--------------------|-----------------|--------------| ------|
| sls           | SLS 日志查询         | prod/test/uat   | 内部           | ✅    |
| mysql         | MySQL/PolarDB 查询   | test/uat        | 内部           | ✅    |
| redis         | Redis 缓存状态查询    | test/uat        | 内部           | ✅    |
| elasticsearch | ES 全文检索           | test-finance    | 内部           | ✅    |
| platform      | Doris 分析数据查询    | 仅 prod         | 外部（需确认）  | ✅    |
```

内部 adapter 直接使用；platform（JDBC）需用户确认后才能调用。

**② 排查流程定义**

8步顺序执行总览表，每步含触发条件、执行逻辑摘要、完成标志、引用文件。**交互细节和格式示例全部在引用文件中，SKILL.md 不重复定义。**

**③ 安全规则引用**

声明所有查询操作必须经过安全门控，引用 guards/ 目录。prod SQL EXPLAIN 三档强卡细节见 `guards/sql-safety.md`（唯一权威来源）。

**④ 交互原则与执行模式**

定义两种执行模式：
- **自动模式（0/1/2/3）**：方案确认后全自动推进，输出进度表，无需中间确认
- **手动模式（M）**：每步执行前停下来，让用户确认工具/轨道后再执行

强制暂停例外（任何模式均触发）：prod SQL EXPLAIN 🟡中风险或🔴高风险、外部库调用、空结果重试3次仍无结果。

### 4.2 SKILL.md 的内容边界

**应该包含的**：流程骨架总览、能力清单（含类型）、安全约束引用、执行模式定义、文件引用路径

**不应该包含的**：交互格式示例、完整 EXPLAIN 流程、三轨协作细节——这些全部在各自文件中，SKILL.md 只做引用，避免重复和漂移

### 4.3 尺寸控制

SKILL.md 职责是总览 + 约束 + 引用，不是把子文件内容搬进来。超出边界的内容应拆到对应子文件。

## 第五章：Adapter 能力层

### 5.1 约定规范（`_convention.md`）

每个 adapter 必须是一个独立目录，包含以下文件：

| 文件 | 必须 | 职责 |
|------|------|------|
| `README.md` | ✅ | 告诉 AI：这个 adapter 做什么、怎么用、参数格式、返回结构、注意事项 |
| `client.py` | ✅ | Python 客户端封装。必须从 config.yaml 读取连接参数，必须实现 `health_check()` |
| `config.yaml` | ✅ | 连接参数模板。敏感值用 `${ENV_VAR_NAME}` 环境变量引用；必须有 `enabled` 开关 |
| `requirements.txt` | ✅ | Python 依赖声明 |

### 5.2 内部 vs 外部 Adapter

| 类型 | Adapter | 使用方式 |
|------|---------|---------|
| 内部 | sls / mysql / redis / elasticsearch | 直接使用，无需用户确认 |
| 外部（JDBC） | platform（Doris） | 每次调用前输出确认提示，等用户确认后才执行 |

**外部库确认格式**（见 SKILL.md 工具优先级节）：

```
⚠️ 当前步骤需要使用外部库：platform（Doris JDBC）
原因：内部 adapter 不覆盖该数据源

**[确认使用]** **[换内部方案]** **[跳过此步]**
```

### 5.3 各 Adapter 简介

SLS、Platform、MySQL、Redis、ES 能力详见原 v1.0 文档第五章，此处不重复。核心变化：

- **环境覆盖**：mysql / redis 只覆盖 test/uat，prod 业务数据库通过 platform（Doris）访问
- **platform 标记为外部**：每次调用需用户确认，在工具清单中标注 `[外部 ⚠️ 需确认]`

## 第六章：Guards 安全门控层

安全层是整个 skill 中**唯一不可被 AI 自行绕过的约束**。

### 6.1 SQL 安全（`guards/sql-safety.md`）—— 唯一权威来源

> 所有涉及 EXPLAIN 的规则、交互格式、内联标注规范均以 `guards/sql-safety.md` 为准。其他文件（SKILL.md、query-planning.md、result-analysis.md）只做引用，不重复定义。

#### 6.1.1 语句白名单

只允许 SELECT / SHOW / DESC / EXPLAIN，禁止所有 DDL/DML。详见 sql-safety.md。

#### 6.1.2 EXPLAIN 三档强卡（prod 环境，任何模式不可绕过）

```
prod 环境 SQL 生成后
  ↓
强卡执行 EXPLAIN {SQL}
  ↓
风险判定（满足任一触发）：

🟢 低风险：rows < 10万 且 type ≠ ALL 且 key 非 NULL
   → 自动执行，输出「✅ EXPLAIN 通过（type=range, rows≈1,200, key=idx_user_id）执行中…」

🟡 中风险：rows 10万~100万；或 key=NULL 但 type ≠ ALL
   → 黄色警告卡片，等待 [确认执行] / [我来改写 SQL] / [跳过此步]

🔴 高风险：rows > 100万；或 type=ALL（全表扫描）；或 AI 综合判断有严重性能风险
   → 红色警告卡片，必须明确回复「确认执行」才能继续
```

**强卡原则**：自动模式、手动模式、重试流程，任何情况下都不可绕过。

test/uat 环境：只走白名单检查，跳过 EXPLAIN，直接执行。

#### 6.1.3 分区表保护

Doris 分区表查询必须包含 `dt_month = 'YYYY-MM-01'`。AI 自动从实体池推断补充，不打断用户。涉及分区表：
- `ods_order_cdc.ods_order_s_t_charging_record_history`
- `ods_order_cdc.ods_order_d_t_pay_detail`
- `ods_finance_cdc.ods_finance_d_t_user_flow`

#### 6.1.4 EXPLAIN 结果内联标注（排查过程卡片）

| 风险等级 | 内联标注示例 |
|---------|------------|
| 🟢 低风险 | `mysql/prod（EXPLAIN ✅ type=range, rows≈1,200, key=idx_user_id）` |
| 🟡 中风险 | `mysql/prod（EXPLAIN 🟡 rows≈68万, key=NULL，用户已确认）` |
| 🔴 高风险已确认 | `mysql/prod（EXPLAIN 🔴 type=ALL, rows≈230万，用户确认执行）` |
| 🔴 高风险已跳过 | `mysql/prod（EXPLAIN 🔴 type=ALL, rows≈230万，用户跳过）` |

### 6.2 Redis 安全 / ES 安全 / 数据脱敏

详见 v1.0 文档第六章 6.2-6.4 节，内容无变化。

### 6.3 临时文件管理（`guards/temp-files.yaml`）—— 已更新

| 规则 | 值 |
|------|-----|
| 根目录 | `/tmp/investigation/` |
| 目录格式 | `{date}_{short_uuid}/`（每次排查独立目录） |
| 文件命名 | `{adapter}_{timestamp}.{ext}` |
| 单文件上限 | 50 MB |
| 总大小上限 | 200 MB |
| **清理触发** | **Step 8 策略归档完成后自动执行（主触发）；会话异常结束时兜底触发** |
| **是否询问** | **否，归档反馈环节已是唯一交互点，清理不再单独询问** |
| 导出例外 | 用户说「导出结果」时写 `.exported` 标记，阻止自动清理 |
| 过期自动清理 | 24 小时后自动删除 |

**下钻读取规则**（Phase 4，路径和操作方式详见 `guards/temp-files.yaml` drilldown 节）：
- 只读当前 session 目录，不跨 session 访问
- 默认每批 10 条，上限 100 条
- 支持：顺序加载、时间范围过滤、级别过滤、行号定位、全文 grep、导出

## 第九章：Prompts 提示词层

### 9.1 Prompt 设计原则（新增）

每个 prompt 文件是该阶段的**唯一执行规范**，包含：交互格式、完成标志、禁止行为。SKILL.md 只做引用，不重复定义细节，避免两边漂移。

### 9.2 Prompt 清单

| 文件 | 阶段 | 调用时机 | 核心变化 |
|------|------|---------|---------|

### 9.3 query-planning.md 核心变化

#### 日志轨强制子流程（新增，不可跳步）

进入日志轨后必须完整走完四步，不得在第一步停下来就报告：

```
第一步：关键字宽查日志
  · 用 userId / 订单号 / 业务关键字 宽范围查 SLS
  · 目的：命中相关日志，找到链路入口
  ↓
第二步：提取链路 ID（强制）
  · 从命中日志中提取 traceId / tlogId / requestId
  · 若无链路ID → 扩大时间窗重试，最多3次
  · 确实无链路ID → 标注「⚠️ 无链路ID」，用时间窗替代继续
  ↓
第三步：拉全链路日志（有链路ID时强制）
  · 用 traceId/tlogId 拉完整调用链
  · 重点：ERROR/WARN 条目、超时节点、异常堆栈首次出现
  ↓
第四步：从链路提取线索 → 触发代码轨
  · 识别接口名 / 类名 / 方法名 / 表名 / Redis key
  · 立刻带着线索读对应代码 → 再进入数据轨验证
```

**日志轨禁止行为**：

| ❌ 禁止 | ✅ 正确 |
|--------|--------|
| 查到日志直接报告，不提取链路ID | 命中日志 → 立刻找 traceId/tlogId → 拉全链路 |
| 有链路ID但不拉全链路 | 有链路ID就必须拉全链路，强制步骤 |
| 全链路分析完不读代码 | 从链路日志找到类名 → 立刻读代码 |
| 无链路ID就放弃日志轨 | 无链路ID → 用时间窗+userId继续查 |

```
    │

    │                                      │

    └─────────────┬────────────────────────┘

    │  prod SQL：强卡 EXPLAIN 三档（🟢自动/🟡等确认/🔴必须明确确认）
    │  外部库（platform）：强卡用户确认
    │  所有结果：脱敏
    │
    ▼
Step 6: 执行查询 ──── adapters/<n>/client.py
    │
    │  自动模式：全自动推进，输出进度表
    │  手动模式：每步停下确认工具/轨道
    │
    │  🟡日志轨强制四步（不可跳步）：
    │    关键字宽查 → 提取traceId/tlogId → 拉全链路 → 触发代码轨
```

### 10.2 执行模式

| 模式 | 触发 | 行为 |
|------|------|------|
| 自动模式（0/1/2/3） | 首轮回复用户选择 | 方案确认后全自动推进，输出每步进度表，不中途停下 |
| 手动模式（M） | 首轮回复用户选 M | 每步执行前停下来，让用户确认工具/轨道后执行 |

无论哪种模式，以下情况强制暂停：
- prod SQL EXPLAIN 判定为 🟡中风险或🔴高风险
- 需要调用外部库（platform JDBC）
- 空结果重试 3 次仍无结果

### 10.3 工具优先级

```
  ↓
其他外部方式 → 禁止
```

1. **概览统计**：匹配总数/时间分布/级别分布/去重异常类型（不消耗上下文）
2. **智能采样**：首条+末条+所有ERROR+状态变化点+异常堆栈首次出现；字段裁剪去掉基础设施字段
3. **临时文件兜底**：超阈值时完整结果写文件，AI 只保留采样结果
4. **按需下钻**：「看更多」「看所有ERROR」「搜索xxx」「导出结果」——路径规则见 `guards/temp-files.yaml`

## 第一章：背景与目标

### 1.1 现状与痛点

云快充业务体系包含 30+ 微服务、覆盖 C端（用户 App）和 B端（omp-shop 商户管理后台）。线上问题排查面临以下困境：

**数据分散**：排查一个问题通常需要横跨 SLS 日志、Doris 数据仓库、甚至多个服务的代码，手动在多个系统间切换、拼接查询语句，效率极低。

**经验难沉淀**：每位开发者都有自己习惯的排查路径和关键字，新人面对同类问题需要从头摸索。排查经验散落在个人脑中，无法被团队复用。

**C端与B端割裂**：C端无前端代码，只能通过日志和数据反推用户行为；B端有完整的 omp-shop 前端，可以通过「页面 → 接口 → 日志」三层联动定位问题。两种排查路径完全不同，目前没有统一的方法论。

**安全性缺失**：直接在生产数据库上执行 SQL 没有任何防护，存在误执行高代价查询（全表扫描亿级数据）甚至误操作的风险。

### 1.2 目标

构建一个 Cursor Agent Skill，名为 `compass`（罗盘），实现：

| 目标 | 描述 |
|------|------|
| **自然语言驱动** | 用户用自然语言描述问题（含手机号、订单号、昵称等线索），AI 自动识别实体、规划查询 |
| **内置查询能力** | 通过 Python 脚本直接调用 SLS SDK、平台 HTTP、MySQL、Redis、Elasticsearch，不依赖外部 MCP |
| **安全门控** | SQL 预检、Redis/ES 命令分级、EXPLAIN 评估、用户确认、数据脱敏、审计日志 |
| **约定驱动扩展** | 未来新增 Nacos/MQ 等数据源时，AI 按约定自主创建 adapter，无损引入 |
| **自我进化** | 每次排查后自动归档策略，基于用户反馈调整策略权重，记忆越用越准 |
| **用户监督** | 所有关键决策（查询方案、SQL 执行、策略淘汰）必须经用户确认 |

### 1.3 成功标准

- 一个完整排查流程从用户描述到定位原因，平均交互轮次 ≤ 5 轮
- 新增一个 adapter 所需的人工操作 ≤ 1 句话描述 + 1 次确认
- 所有生产查询 100% 经过安全门控，0 条未经确认的写操作
- 排查策略库在使用 1 个月后可覆盖 80% 以上常见问题类型

## 第二章：架构设计

### 2.1 核心思想：约定驱动 + AI 作为运行时

传统软件中，"微内核 + 插件" 需要代码级的注册发现机制。但在 AI Skill 场景下，**AI 本身就是运行时**——它读文件、理解语义、做决策、执行操作。因此不需要传统的插件系统，而是采用「约定即契约」的思想：

- **约定** 替代接口定义：adapter 按固定目录结构和文件命名组织，AI 读取即理解
- **注册表** 是纯文本：SKILL.md 中维护一张 adapter 清单，AI 自己更新
- **扩展** 靠 AI 自身：新增能力时 AI 按约定创建文件，用户确认后生效

这种方式的根本优势是：**扩展能力不需要人写代码**，AI 按约定自主完成。

### 2.3 各层职责

| 层 | 职责 | 修改频率 | 谁维护 |
|----|------|---------|--------|
| **SKILL.md** | 总调度入口。定义排查流程、能力注册表、安全规则引用 | 极低（仅新增 adapter 时加一行注册） | AI + 用户确认 |
| **Prompts** | 各阶段的思考指引。实体提取、场景分类、方案规划、结果分析、策略优化 | 低（随策略优化微调） | AI 优化 + 用户审批 |
| **Guards** | 安全防线。SQL 白名单、EXPLAIN 预检、脱敏规则、查询限制 | 极低（安全策略稳定） | 用户配置 |
| **Memory** | 持久化记忆。查询策略、问题分类、用户决策、审计日志 | 高（每次排查都写入） | AI 自动写入 |
| **Adapters** | 外部数据源能力封装。每个 adapter 自包含（client + config + README） | 中（新增/调整数据源时） | AI 创建 + 用户确认 |
| **Knowledge** | 业务知识。系统拓扑、页面-接口映射、数据表文档、项目描述 | 中（新增项目/页面时） | AI 探索生成 + 用户确认 |

### 2.4 设计原则

**P1：用户始终拥有最终决策权**
所有涉及数据查询、知识写入、策略淘汰的操作，必须经过用户明确确认。AI 负责提案，用户负责审批。对于已经确认过的通用决策，记录后复用，不重复询问。

**P2：约定优于配置**
adapter 不需要注册声明文件（如 plugin.yaml），只要目录结构和文件命名符合约定，AI 就能识别和使用。这降低了扩展成本，也让 AI 能够自主创建新 adapter。

**P3：按需加载，不预读全部**
AI 在收到用户问题后，先判断需要哪些能力，再读取对应 adapter 的 README 和 knowledge。不在一开始就加载全部文件，节省 context window。

**P4：渐进式知识积累**
knowledge/ 和 memory/ 初始都为空。通过使用逐步积累，每一次排查都在为下一次铺路。但积累必须有边界——内置压缩和过时淘汰机制，防止信息膨胀。

**P5：无损扩展**
新增 adapter 时：① 新建独立目录 ② 更新 SKILL.md 注册表加一行。不修改任何已有文件的内部逻辑。adapter 通过 config.yaml 中的 `enabled` 字段实现开关控制。

## 第四章：SKILL.md 设计

SKILL.md 是整个 skill 的大脑。它不处理具体业务逻辑，而是定义「做事的方式」。目标是写一次基本不再修改（除了能力注册表加行）。

### 4.1 SKILL.md 的四大职责

**① 能力注册表**

以纯文本表格形式维护可用 adapter 清单。AI 通过此表知道自己有哪些能力，新增 adapter 时只需加一行：

```
| Adapter       | 用途                | 适用场景         | 状态     |
|---------------|--------------------|-----------------| ---------|
| sls           | SLS 日志查询         | 全场景           | ✅ 可用  |
| platform      | Doris 数据查询       | 全场景           | ✅ 可用  |
| mysql         | MySQL/PolarDB 查询   | 业务数据排查      | ✅ 可用  |
| redis         | Redis 缓存状态查询    | 实时状态排查      | ✅ 可用  |
| elasticsearch | ES 全文检索/聚合      | 日志/文档检索     | ✅ 可用  |
```

AI 只使用「状态=✅ 可用」的 adapter。新 adapter 初始标记为「⏳ 待验证」，health_check 通过后才改为「✅ 可用」。

**② 排查流程定义**

按步骤定义从「用户输入」到「给出结论」的完整流程，每步引用对应的 prompt 文件。流程本身不包含具体逻辑，只是编排顺序和分支条件。详见第十章。

**③ 安全规则引用**

声明所有查询操作必须经过安全门控，并引用 guards/ 目录下的具体规则文件。这是一条硬性约束，不可被 prompt 覆盖。

**④ 交互原则**

定义与用户的交互规范：
- 查询方案必须展示给用户确认后再执行
- 已确认的通用决策从 memory/confirmations.yaml 中复用
- 结果分层展示：关键摘要 → 详细数据 → 原始记录
- 排查结束后主动询问用户反馈

### 4.2 SKILL.md 的内容边界

**应该包含的**：流程骨架、能力清单、安全约束引用、交互原则、文件引用路径

**不应该包含的**：具体查询逻辑、SQL 语句、adapter 使用细节、数据表结构——这些全部在各自的文件中，SKILL.md 只做引用

### 4.3 尺寸控制

SKILL.md 必须控制在 **300 行以内**，因为它是每次会话都要读的文件。超过 300 行意味着职责溢出，应将内容拆到 prompts/ 或 adapters/*/README.md 中。

## 第五章：Adapter 能力层

### 5.1 约定规范（`_convention.md`）

每个 adapter 必须是一个独立目录，包含以下文件：

| 文件 | 必须 | 职责 |
|------|------|------|
| `README.md` | ✅ | 告诉 AI：这个 adapter 做什么、怎么用、参数格式、返回结构、注意事项。**这是 AI 使用该 adapter 的唯一指引** |
| `client.py` | ✅ | Python 客户端封装。必须从 config.yaml 读取连接参数，必须实现 `health_check()` 方法 |
| `config.yaml` | ✅ | 连接参数模板。敏感值用 `${ENV_VAR_NAME}` 环境变量引用，实际值写入 `.env` 文件；必须有 `enabled: true/false` 开关 |
| `requirements.txt` | ✅ | Python 依赖声明 |
| `examples.md` | ❌ | 可选，复杂 adapter 的调用示例 |

#### client.py 接口规范

所有 client 必须遵循的约定：

- **构造函数**：接受 `config_path` 参数，从对应 config.yaml 加载配置
- **health_check() → bool**：验证连通性，返回 True/False
- **业务方法**：自由定义，但方法名必须语义清晰（如 `query_logs`、`query_sql`）
- **错误处理**：所有异常必须捕获并返回结构化错误信息，不允许抛出未处理的异常到 AI 层
- **返回格式**：统一返回 dict，包含 `success: bool`、`data: any`、`error: str|None`

#### config.yaml 规范

```yaml
# 第一行必须是 enabled 开关
enabled: true

# 其余字段由 adapter 自定义
# 敏感值使用 YOUR_XXX 占位，用户首次使用时填写
```

#### 公共基类 `adapters/base.py`

为减少 adapter 间的重复代码，提供以下公共基类供新 adapter 使用（现有 adapter 可选迁移）：

| 类 | 适用场景 | 提供的能力 |
|---|---------|-----------|
| `BaseAdapter` | 所有 adapter | 配置加载、YAML 解析校验、`enabled` 检查、禁用响应生成 |
| `MultiProfileAdapter` | MySQL/Redis/ES 等多实例连接 | 在 BaseAdapter 基础上增加 profile 管理、默认 `list_profiles()`（自动过滤敏感字段） |

新 adapter 继承基类的标准用法：

```python
from adapters.base import MultiProfileAdapter

class NewAdapter(MultiProfileAdapter):
    ADAPTER_NAME = "new-adapter"
    REQUIRED_CONFIG_KEYS = ["profiles"]  # 缺失时构造函数抛 ValueError

    def __init__(self, config_path=None):
        super().__init__(config_path, caller_file=__file__)

    def health_check(self) -> bool:
        if not self.enabled:
            return False
        # ... 具体连通性检查
```

工具函数：

- `validate_config(cfg, required_keys, adapter_name)`：校验必需字段，缺失时列出所有缺失项

## 第六章：Guards 安全门控层

安全层是整个 skill 中**唯一不可被 AI 自行绕过的约束**。SKILL.md 中以硬性规则形式引用，任何查询操作执行前必须经过安全门控。

### 6.1 SQL 安全（`guards/sql-safety.md`）

#### 6.1.1 语句白名单

只允许以下 SQL 语句类型通过：

| 允许 | 禁止 |
|------|------|
| `SELECT` | `DELETE`、`UPDATE`、`INSERT`、`DROP`、`ALTER`、`TRUNCATE`、`CREATE`、`GRANT`、`REVOKE` |
| `SHOW`（DATABASES、TABLES、COLUMNS） | 任何 DDL/DML 操作 |
| `DESC` / `DESCRIBE` | `CALL`、`EXECUTE` |
| `EXPLAIN` | 存储过程调用 |

AI 生成 SQL 后，必须先做关键字检查。如果包含禁止列表中的关键字，直接拒绝并告知用户。

#### 6.1.2 EXPLAIN 预评估流程

```
AI 生成 SQL
    ↓
关键字检查 → 通过？
    ↓ 是
EXPLAIN {SQL} → 获取执行计划
    ↓
评估扫描行数
    ↓
    ├── < 10 万行 → 正常执行（展示给用户确认后执行）
    ├── 10万 ~ 100万行 → 黄色警告：展示预估行数，建议加过滤条件
    └── > 100 万行 → 红色警告：强烈建议缩小范围，需用户明确输入"确认执行"
```

#### 6.1.3 分区表保护

Doris 分区表（如 `ods_order_s_t_charging_record_history`）查询必须包含分区字段 `dt_month` 的过滤条件。AI 在生成 SQL 时需检查目标表是否为分区表（参照 knowledge/tables/ 中的标注），如果是则必须包含 `WHERE dt_month = 'YYYY-MM-01'`。

#### 6.1.4 用户确认流程

所有 SQL 在实际执行前，必须展示给用户：

```
AI: "我准备执行以下查询："

    SQL: SELECT record_id, trade_seq, ...
         FROM ods_order_cdc.ods_order_s_t_charging_record_history
         WHERE dt_month = '2025-03-01' AND uid = 541324
         LIMIT 10

    预估：扫描约 2.6 万行，返回 ≤ 10 条

    确认执行？

用户: 确认 / 调整 / 取消
```

**例外**：如果 memory/confirmations.yaml 中记录了「低风险查询无需逐条确认」的决策，则扫描 < 10 万行的 SELECT 可跳过确认。但首次使用时必须问。

### 6.2 Redis 安全（`guards/redis-safety.md`）

Redis adapter 只暴露只读方法，安全规则分三级：

| 级别 | 代表命令 | 策略 |
|------|---------|------|
| READ_ONLY | GET, SCAN, HGETALL, TYPE, TTL, INFO | ✅ 允许 |
| WRITE | SET, DEL, EXPIRE, HSET, LPUSH | ❌ 禁止 |
| DANGEROUS | KEYS, FLUSHALL, CONFIG, SHUTDOWN | ❌ 严禁 |

核心规则：禁用 KEYS（用 SCAN 替代）；SCAN 单次上限 100 key；敏感 key 模式（`user:token:*`、`session:*`、`sms:code:*`）需脱敏或完全隐藏值。

### 6.3 ES 安全（`guards/es-safety.md`）

ES adapter 只暴露查询方法，安全规则分四级：

| 级别 | 代表操作 | 策略 |
|------|---------|------|
| READ_ONLY | _search, _count, _mapping, _cat | ✅ 允许 |
| WRITE | index, _update, _delete, _bulk | ❌ 禁止 |
| DANGEROUS | _delete_by_query, _reindex | ❌ 严禁 |
| ADMIN | _create(index), _template, _snapshot | ❌ 严禁 |

核心规则：`size` 上限 100；`from + size` 不超过 10000（深分页防护）；禁止全索引通配符 `*` 搜索；聚合 terms size 不超过 1000。

### 6.4 数据脱敏（`guards/data-masking.md`）

查询结果展示给用户时，以下字段做脱敏处理：

**必须脱敏（PII 字段）**：

| 字段类型 | 原始值 | 脱敏后 |
|---------|--------|--------|
| 手机号 | 13900000002 | 139****0002 |
| 身份证号 | 110000199001010000 | 110000****0000 |
| 银行卡号 | 6222021234567890 | 6222****7890 |
| 邮箱地址 | example@example.com | ex****@example.com |
| 车牌号 | 苏A12345 | 苏A****5 |
| 地址 | 江苏省南京市鼓楼区... | 江苏省南京市**** |
| 姓名 | 张三 | 张* |

**完全隐藏（敏感凭证）**：

| 字段类型 | 原始值 | 脱敏后 |
|---------|--------|--------|
| 密码/密钥 | abc123xyz | ****** |
| 支付宝/微信 ID | 2088xxxx | 2088**** |
| Cookie/Session/JWT | eyJhbGci... | ****** |

字段名匹配大小写不敏感、下划线不敏感，同时结合值的格式（如 11 位 1 开头 → 手机号）双重判断。临时文件存原始数据，仅在展示时脱敏。用户明确要求「展示完整手机号」时可一次性展示，但记录到审计日志。

### 6.5 临时文件管理（`guards/temp-files.yaml`）

排查过程中产生的中间结果文件（SLS 日志、MySQL 导出等）遵循以下规范：

| 规则 | 值 |
|------|-----|
| 根目录 | `/tmp/investigation/` |
| 目录格式 | `{date}_{short_uuid}/`（每次排查独立目录） |
| 文件命名 | `{adapter}_{timestamp}.{ext}` |
| 单文件上限 | 50 MB |
| 总大小上限 | 200 MB |
| 会话最大文件数 | 20 |
| 过期自动清理 | 24 小时后自动删除 |
| 会话结束行为 | 询问用户是否保留，默认清理 |

安全约束：文件名不含用户 ID / 手机号等敏感信息；文件权限 600（仅当前用户可读写）。

### 6.6 查询限制（`guards/query-limits.yaml`）

  max_limit: 100                    # 单次查询最多返回行数

## 第七章：Knowledge 知识层

知识层是 AI 理解业务系统的基础。分为两类平行插件：**Projects（代码导航）** 和 **Knowledge（业务知识）**，初始全部为空，通过「入驻工作流」由 AI 探索代码后生成，用户确认后落盘。

### 7.1 核心思想：代码导航 > 静态描述

传统方式：`projects/*.md` 存静态功能描述 → AI 只知道模块名称，排查靠猜测。

**现在**：`projects/*.md` 存 **代码路径导航**（Controller、Service、Mapper 的文件路径），排查时 AI 按路径去读**活代码**，获得一手理解。

```
知识 = 导航坐标（告诉 AI 去哪读）
代码 = 真实信息源（AI 实际读的内容）
```

对比示例：
- 旧：`projects/finance_server.md` 写 "钱包服务 — 充值/扣款" → AI 只知道功能名
- 新：`projects/finance_server.md` 写代码路径表 → AI 读 `WalletServiceImpl.java` → 知道先查 Redis 再查 DB、用什么事务、抛什么异常

### 7.2 两类插件

| 插件类型 | 路径 | 作用 | 排查中的角色 |
|---------|------|------|------------|
| Projects 代码导航 | `projects/*.md` | 代码在哪、怎么读 | 告诉 AI **查什么**（表名、key、关键字来自代码） |
| Adapters 数据源 | `adapters/*/` | 数据在哪、怎么查 | 告诉 AI **怎么查**（执行查询） |

两者共同支撑排查：代码导航提供方向，adapter 提供能力。

### 7.3 知识分类

| 类型 | 路径 | 内容 | 生成方式 |
|------|------|------|---------|
| **代码导航地图** | `projects/*.md` | Controller/Service/Mapper 路径表 + 排查入口映射 | AI 扫描代码目录生成（插件化，一文件一服务） |
| 系统拓扑 | `knowledge/systems.md` | C端/B端划分、服务列表、服务间关系 | AI 根据用户描述 + workspace-index.yaml 生成 |
| B端页面知识 | `knowledge/b-side/*.yaml` | 页面路由、页面→接口、接口→日志关键字 | AI 探索 omp-shop 代码生成 |
| 数据表知识 | `knowledge/tables/*.yaml` | 表结构（按约定 YAML 格式）、分区标注、常用查询 | AI 通过 `DESC` + 采样查询生成 |

### 7.4 代码导航地图（`projects/`）

### 7.5 排查流程中代码的使用方式

排查中新增 **Step 3: 代码理解**（在场景分类和查询规划之间）：

```
Step 2: 场景分类 → 识别涉及哪个服务
    ↓
Step 3 [代码理解]:
    1. 读 projects/<service>.md → 获得代码路径表
    2. B 端问题：先读前端项目 → 找到页面+API → 跳到后端项目
    3. 按"排查路径"表找到入口代码
    4. 读入口 Controller/Service 的实际代码
       → 理解业务逻辑、异常分支、涉及的表和缓存
    5. 用代码理解指导 Step 4 的查询规划
    ↓
Step 4: 查询规划（基于代码理解，而非猜测）
```

**示例**：群里有人说"某个司机钱包余额显示为 0"

```
1. 实体提取: 司机ID/手机号
2. 场景分类: B端 → 钱包相关
3. [代码理解]:
   - 读 projects/omp-shop.md → 钱包页面 → API: GET /finance/wallet/balance
   - 读 projects/finance_server.md → 排查入口: WalletServiceImpl#getBalance
   - AI 读 WalletServiceImpl.java 的 getBalance 方法
   - 发现: 先查 Redis(wallet:balance:{orgId}:{userId})，未命中才查 t_user_wallet
4. 查询规划（基于代码理解）:
   - Step A [redis] 查 wallet:balance:{orgId}:{driverId} 看缓存值
   - Step B [mysql] 查 t_user_wallet WHERE user_id = {driverId} 看 DB 值
   - Step C [sls] 搜 "walletOperate" AND {driverId} 看最近操作日志
5. 结果分析: Redis=0, DB=100 → 缓存不一致 → SLS 显示 adjustBalance 没刷缓存
```

### 7.6 系统拓扑（`knowledge/systems.md`）

描述整个业务系统的宏观结构，帮助 AI 在场景分类阶段做出正确判断。内容包括：

- **C端**：用户 App，无前端代码，排查只能依赖日志和数据库。主要后端服务：order_server、charge_server、finance_server
- **B端**：omp-shop 商户管理后台，有完整前端代码，可通过「页面→接口→日志」三层追溯。关联后端服务：finance_server、base_server 等
- **服务间调用关系**：哪些服务之间有依赖（如订单服务调用支付服务，支付服务调用财务服务）

### 7.7 B端页面知识（`knowledge/b-side/`）

三个 YAML 文件形成完整的「页面→接口→日志」追溯链：

**pages.yaml** — 页面目录

```yaml
pages:
  - id: "wallet-management"
    name: "管理账户余额"
    route: "/customerManagement/vehicleFleetManagement/walletManagement"
    description: "对子机构和司机进行额度分配与回收"
    source_project: "omp-shop"
    generated_at: "2026-03-28"
```

**page-api-mapping.yaml** — 页面到接口

```yaml
mappings:
  - page_id: "wallet-management"
    apis:
      - method: "POST"
        path: "/api/wallet/batch-adjust"
        service: "finance_server"
        description: "批量额度调整"
```

**api-log-keywords.yaml** — 接口到日志关键字

```yaml
keywords:
  - api_path: "/api/wallet/batch-adjust"
    container: "finance-server"
    sls_keywords: ["batchAdjust", "walletAdjustRecord"]
    error_keywords: ["InsufficientBalance", "WalletAdjustException"]
```

### 7.8 数据表文档（`knowledge/tables/`）

数据表知识按约定（`tables/_convention.md`）以 YAML 格式组织，当前统一放在 `common_tables.yaml` 中。每个表的描述包括：

- 表名和所属数据源（Doris / MySQL / Redis）
- 是否为分区表（⚠️ 标注分区键）
- 关键字段清单（名称、类型、业务含义）
- 枚举值说明（如 `trade_status: 1=充电中, 3=已完成, 4=异常`）
- 常用查询模式（按用户查、按订单查、按时间查）
- 注意事项（如 Redis key 的过期策略、Doris 必须带分区条件等）

随着排查实践增多，AI 可按约定扩展为多个 YAML 文件（如 `order_tables.yaml`、`finance_tables.yaml`）。

### 7.9 知识生命周期

```
空白 → 入驻生成 → 使用中 → 过时检测 → 更新/淘汰
```

**过时检测增强**：
- 代码路径不存在（文件被移动/重命名）→ 标记 `stale`，提醒更新
- 接口路径变化（Controller 注解改了）→ 提醒重新扫描
- 页面路由变化（前端路由定义改了）→ 提醒更新前端项目文件
- 每个 `.md` 文件有 `last_verified` 时间戳用于新鲜度判断

**知识缺口检测**：排查过程中如果涉及某服务但 `projects/` 下没有对应文件 → 记录缺口 → 排查结束后提示用户注册

**更新触发**：用户可随时说「更新 XX 的知识」或「刷新 XX」，AI 重新扫描代码并展示 diff。确认后全量覆盖——避免新旧信息混杂。

**越用越准**：排查结束后的策略归档会关联用到的 project 文件——哪些代码路径帮助了定位 → 记录到策略中 → 下次同类问题直接指向有效的代码入口。

## 第八章：Memory 记忆层

记忆层是 skill 自我进化的基础。与 knowledge（客观事实）不同，memory 存储的是**主观经验**——什么策略有效、用户偏好什么、哪类问题常见。

### 8.1 文件清单

| 文件 | 职责 | 写入时机 | 上限管理 |
|------|------|---------|---------|
| `strategies.yaml` | 查询策略库 | 每次排查成功后 | 超 50 条触发自动合并/淘汰 |
| `archived-strategies.yaml` | 已归档策略 | 策略被合并或淘汰时 | 无上限（历史记录） |
| `categories.yaml` | 问题分类库 | 每次排查后归类 | 自然去重 |
| `confirmations.yaml` | 用户通用决策 | 用户做出可复用决策时 | 无上限（条目少） |
| `audit-log.yaml` | 执行审计日志 | 每次执行查询时 | 超 500 条归档旧记录 |

### 8.2 查询策略库（`strategies.yaml`）

策略不是固定模板，是**从实际排查中学来的经验**。每条策略记录四个维度：

#### 8.2.1 策略结构

```yaml
strategies:
  - id: "stg_001"
    # ① pattern — 什么问题（用于匹配）
    pattern:
      category: "钱包-余额异常"
      keywords: ["余额", "显示为0", "余额不对", "钱包"]
      entity_types: ["user_id", "org_id"]
      services: ["finance_server"]
      scene: "b-side"

    # ② plan — 怎么查（查询路径）
    plan:
      - step: 1
        adapter: "redis"
        action: "查钱包缓存"
        template: "GET wallet:balance:{org_id}:{user_id}"
        source: "WalletServiceImpl#getBalance"    # 来自哪段代码
        parallel_with: null
        depends_on: null
      - step: 2
        adapter: "mysql"
        action: "查DB钱包表对比"
        template: "SELECT available_amount FROM t_user_wallet WHERE user_id = {user_id}"
        source: "WalletMapper.xml"
        parallel_with: 1                           # 可与 step 1 并行
        depends_on: null
      - step: 3
        adapter: "sls"
        action: "查最近钱包操作日志"
        template: "walletOperate AND {user_id}"
        source: "WalletServiceImpl"
        parallel_with: null
        depends_on: null

    # ③ score — 效果如何（用于排序）
    score:
      effectiveness: 0.92         # 成功定位问题的比率
      usage_count: 14             # 被采用次数
      last_used: "2026-03-28"
      avg_rounds: 1.3             # 平均几轮查到原因
      user_ratings: [5, 4, 5, 5]  # 用户打分历史
      modification_count: 1       # 用户微调次数

    # ④ meta — 来源信息
    meta:
      created_at: "2026-03-15"
      created_from: "first_use"   # first_use / merged / optimized / preset
      last_updated: "2026-03-28"
      related_projects: ["finance_server"]  # 关联的代码导航
```

#### 8.2.2 策略匹配机制

AI 不是简单的关键字匹配，而是多维度加权评分：

```
总分 = W_cat × 类别匹配度       (0.30)
     + W_kw  × 关键字命中率      (0.20)
     + W_ent × 实体类型覆盖度    (0.10)
     + W_svc × 服务匹配度        (0.15)
     + W_eff × effectiveness    (0.15)
     + W_rec × 时间衰减因子      (0.10)
```

权重存储在 `strategies.yaml` 的 `matching_weights` 配置中，可调优。

评分 >= 0.4 的策略按分数降序展示 Top 3 给用户选择：

```
找到 3 个历史排查策略：

  ⭐ 策略 A「钱包-余额异常」（匹配 94%，用 14 次，成功率 92%）
  策略 B「钱包-充值未到账」（匹配 78%，用 6 次，成功率 83%）
  策略 C「账户冻结异常」  （匹配 65%，用 3 次，成功率 67%）

选择策略？或从零规划？[A / B / C / 新建]
```

#### 8.2.3 预设策略

`strategies.yaml` 中有 `presets` 列表，是 AI 的初始经验种子：
- 初始内置几个常见场景（钱包余额、支付失败、充电卡住）
- 首次匹配使用后，复制到 `strategies` 列表并开始积累 score
- 预设策略的 `created_from` 为 `"preset"`

#### 8.2.4 策略生命周期

```
新问题(无匹配) → AI 从零规划 → 成功 → 归档为新策略(score初始化)
                                        ↓
有匹配策略 → 展示给用户 → 选择/微调 → 执行 → 更新 score
                                        ↓
                               usage_count++, effectiveness 更新
                                        ↓
                         自动检查：合并 / 淘汰 / 进化
```

#### 8.2.5 上限管理与自优化（全自动）

策略生命周期管理**完全由 AI 自动执行**，不需要用户逐条决策。操作完成后以简报通知。

**保护规则**（不可触碰的策略）：

| 保护条件 | 说明 |
|---------|------|
| `pinned: true` | 用户手动标记为「保留」/「不可删」的策略 |
| 最近 5 次排查使用过 | 活跃策略不应被合并或淘汰 |
| `presets` 中的原始策略 | 预设策略永远保留作为基准 |

**自动管理机制**：

| 机制 | 触发条件 | 自动操作 |
|------|---------|---------|
| **合并** | 同 category 下策略数 > 5 | 排除受保护策略，合并相似度 >= 70% 的，保留最佳路径，旧策略归档 |
| **淘汰** | 总数 > 50 | 排除受保护策略，淘汰 effectiveness < 0.3 或 180天未用的 |
| **进化** | modification_count >= 3 | 用最近成功路径自动更新默认 plan，重置微调计数 |

操作后通知示例：`[策略维护] 自动合并了「钱包-余额异常」下 3 个相似策略，归档 2 个低效策略。`

#### 8.2.6 AI 的完整上下文感知

排查时 AI 的七层上下文：

| 层 | 来源 | 提供什么 |
|----|------|---------|
| 能力 | `adapters/` | 有哪些查询工具，怎么调用 |
| 代码 | `projects/` | 代码在哪，业务逻辑是什么 |
| 知识 | `knowledge/` | 系统拓扑、页面映射、表结构 |
| 经验 | `memory/strategies.yaml` | 历史上类似问题怎么查的 |
| 分类 | `memory/categories.yaml` | 问题分类体系 |
| 偏好 | `memory/confirmations.yaml` | 用户的通用决策 |
| 约束 | `guards/` | 安全限制、上下文限制 |

查询方案是基于这七层上下文的综合判断，不是固定模板。

### 8.3 问题分类库（`categories.yaml`）

记录已知问题类型，帮助 AI 在场景分类阶段快速归类：

```yaml
categories:
  - id: "cat-001"
    name: "充电订单-支付失败"
    keywords: ["支付失败", "扣费", "余额不足", "支付异常"]
    scene: "c-side"
    frequency: 12                # 累计出现次数

  - id: "cat-002"
    name: "B端-页面数据不展示"
    keywords: ["页面空白", "列表不显示", "加载失败"]
    scene: "b-side"
    frequency: 5
```

### 8.4 用户通用决策（`confirmations.yaml`）

避免每次排查都重复问相同的问题：

```yaml
confirmations:
  - question: "默认查 prod 环境？"
    answer: true
    confirmed_at: "2026-03-28"

  - question: "低风险 SELECT 查询（< 10万行）是否无需逐条确认？"
    answer: true
    confirmed_at: "2026-03-28"

  - question: "是否默认并行查询 SLS + Platform？"
    answer: true
    confirmed_at: "2026-03-28"
```

AI 在排查过程中遇到对应场景时，直接复用已有决策，不再询问。用户可随时说「重置决策」来清除某条或全部。

### 8.5 审计日志（`audit-log.yaml`）

详见第六章 6.4 节。此处补充归档规则：

- 审计日志只追加不修改
- 超过 500 条时，将 30 天前的记录自动移入 `memory/audit-archive/YYYY-MM.yaml`
- 归档操作在排查结束后执行，不在排查过程中打断
- 归档需用户确认（首次确认后记入 confirmations.yaml，后续自动执行）

## 第九章：Prompts 提示词层

Prompts 是 AI 在各阶段的「思考指引」。每个 prompt 文件对应排查流程中的一个阶段，告诉 AI 在这个阶段应该做什么、怎么思考、输出什么。

### 9.1 Prompt 设计原则

- **每个 prompt 单一职责**：一个文件只指导一个阶段
- **声明输入和输出**：明确这个阶段接收什么、产出什么
- **可被 AI 优化**：AI 在 strategy-improvement 阶段可以建议修改 prompt（但需用户批准）
- **不含具体数据**：SQL 模板、表结构等放在 knowledge/ 和 adapters/ 中，prompt 只引用

### 9.2 Prompt 清单

| 文件 | 阶段 | 调用时机 | 读取频率 |
|------|------|---------|---------|
| `entity-extraction.md` | 实体提取 | 收到用户描述时 | 每次排查 |
| `classify-scene.md` | 场景分类 | 实体提取后 | 每次排查 |
| `query-planning.md` | 查询规划 | 场景分类后 | 每次排查 |
| `result-analysis.md` | 结果分析 | 查询执行后 | 每次排查 |
| `strategy-improvement.md` | 策略归档 | 排查结束后 | 每次排查 |
| `project-onboarding.md` | 项目入驻 | 用户触发时 | 偶尔 |
| `knowledge-onboarding.md` | 知识入驻（单页面） | 用户触发时 | 偶尔 |
| `knowledge-batch-scan.md` | 批量扫描入驻（整个服务） | 用户触发时 | 偶尔 |
| `lite-flow.md` | 低阶模型精简流程 | 模型能力不足或用户要求简化时 | 按需 |

### 9.3 各 Prompt 详细规格

#### `entity-extraction.md` — 实体提取

**职责**：从用户自然语言描述中识别可用于查询的实体

**输入**：用户的自然语言描述

**输出**：结构化实体列表

**需要识别的实体类型**：

| 实体 | 示例 | 用途 |
|------|------|------|
| 用户手机号 | 138xxxxxxxx | 查用户表，获取 user_id |
| 用户昵称 | "张三" | 模糊查用户表 |
| 用户 ID | 541324 | 直接查订单、流水 |
| 订单号/record_id | 598002873 | 直接查订单详情 |
| 交易流水号 | 320101000... | 查支付、查日志 |
| 充电桩号/gun_id | 20172 | 查设备相关订单 |
| 电站名称/station_id | "望京站" / 26035 | 查电站相关记录 |
| 时间范围 | "今天"/"昨天下午"/"3月15日" | 确定查询时间窗口 |
| 运营商 | "某某运营商" | 缩小数据范围 |

**特殊处理**：如果用户描述中没有明确的时间范围，默认设定为「最近 24 小时」并告知用户。

---

#### `classify-scene.md` — 场景分类

**职责**：判断问题属于 C端还是 B端，以及具体的问题类别

**输入**：用户描述 + 提取的实体

**输出**：
- `scene`: `c-side` | `b-side` | `unknown`
- `category`: 匹配 memory/categories.yaml 中的类别，或创建新类别
- `required_capabilities`: 需要哪些 adapter

**判断逻辑**：
- 描述中提到「商家后台」「管理页面」「omp」→ B端
- 描述中提到「用户App」「充电」「扫码」「支付」→ C端
- 无法判断 → 问用户

---

#### `query-planning.md` — 查询规划

**职责**：制定查询方案，选择 adapter，生成具体查询语句

**输入**：实体 + 场景 + 问题类别 + 历史策略（如有匹配）

**输出**：查询方案（展示给用户确认）

**核心逻辑**：
1. 检查 memory/strategies.yaml 是否有匹配的历史策略
2. 如有 → 基于历史策略微调（替换实体值）
3. 如无 → 根据实体和场景，从 adapter README 和 knowledge 中组合查询方案
4. B端场景 → 先走 knowledge/b-side 的页面→接口→关键字链路
5. 展示方案给用户：将要查哪些数据源、执行什么查询、预估结果
6. 问用户：是否并行查多个数据源？是否调整？
7. 复用 memory/confirmations.yaml 跳过已决策项

---

#### `result-analysis.md` — 结果分析

**职责**：汇总多源查询结果，给出分析和判断

**输入**：各 adapter 的查询结果 + 会话上下文

**输出**：分层展示的分析报告

**展示结构**：
1. **关键摘要**（2-3 句话说结论）
2. **数据展示**（脱敏后的关键字段，表格形式）
3. **异常分析**（哪些数据点异常、可能原因）
4. **建议操作**（需要进一步查什么、是否需要联系某个服务负责人）
5. **统计信息**（如果用户要求了统计维度）

**后续动作**：如果一轮结果不足以定位问题，自动建议下一步查询方向。

---

#### `strategy-improvement.md` — 策略归档

**职责**：排查结束后，将有效策略写入记忆

**输入**：完整的排查会话（实体、查询、结果、用户反馈）

**输出**：更新 memory/ 下的文件

**执行逻辑**：
1. 询问用户反馈：「这次排查有帮助吗？」
2. 根据反馈打分并记录
3. 如果是新问题类别 → 写入 categories.yaml
4. 如果查询策略有效 → 写入或更新 strategies.yaml
5. 触发记忆压缩检查（详见第十二章）

---

#### `project-onboarding.md` 和 `knowledge-onboarding.md`

详见第十三章。

## 第十章：排查流程设计

### 10.0 模型执行门禁（防「一问就查库」）

大模型默认倾向「立刻帮用户执行」，与本 Skill 设计冲突。须在 `SKILL.md` 中硬性规定：

- **首轮回复禁止**在未完成「实体 + 场景 + 环境/工具可用性说明 + strategies.yaml 匹配展示 + 查询步骤表 + 用户确认」之前，调用任何 adapter（含终端执行 client.py）。
- **策略非固定**：每次重新匹配 `memory/strategies.yaml`；无匹配则现场拟定方案并说明理由。
- **单步失败不收官**：空结果/报错时须给出替代路径并征求继续，不得静默结束。

详见当前版本 `SKILL.md` 文首「首轮回复门禁」与 `prompts/query-planning.md`「执行前硬约束」。

### 10.1 主流程

```
用户输入自然语言描述
    │
    ▼
Step 1: 实体提取 ──── prompts/entity-extraction.md
    │  提取：手机号/ID/订单号/桩号/电站/时间
    │
    ▼
Step 2: 场景分类 ──── prompts/classify-scene.md
    │  判断：C端/B端？读 memory/categories.yaml 匹配问题类别
    │
    ├─── C端 ────────────────────────────┐
    │                                     │
    ▼                                     ▼
Step 3-C: 读 projects/<service>.md   Step 3-B: 页面路径发现
    识别涉及的服务                        读 projects/omp-shop.md
    读代码导航找入口代码                  页面→API→后端服务
    读活代码理解业务逻辑                  跳转 projects/<service>.md
    │                                     读入口代码理解逻辑
    │                                     │
    └─────────────┬───────────────────────┘
                  ▼
Step 4: 查询规划 ──── prompts/query-planning.md
    │  ★ 环境探查：读各 adapter 的 config.yaml，确认目标环境下可用的工具和 profile
    │  ★ 按需选工具：只选解决问题所需的最少 adapter，不全用
    │  ★ 策略匹配：多维度评分，展示 Top 3 历史策略供选择
    │  ★ 多方案时列出全部方向供选择（可多选 + 并行）
    │  每步标注 [adapter → 环境/profile]
    │  展示方案给用户确认
    │
    ▼
Step 5: 安全门控 ──── guards/*
    │  SQL 关键字检查
    │  EXPLAIN 预评估
    │  展示 SQL + 预估成本，用户确认
    │
    ▼
Step 6: 执行查询（支持并行）
    │  按用户选择的方案执行
    │  独立方案可并行（最多 3 个）
    │  调用 adapter client.py
    │  记录审计日志
    │
    ▼
Step 7: 结果分析（分层展示）──── prompts/result-analysis.md
    │  参考 guards/context-limits.yaml 控制上下文
    │  大结果集：概览统计 → 智能采样 → 临时文件兜底
    │  脱敏展示，结合代码逻辑分析
    │  多方案结果交叉分析
    │  用户可按需下钻查看更多
    │
    ├── 需要进一步查？──→ 更新会话上下文 → 回到 Step 4
    │
    ▼
Step 8: 用户反馈 + 策略归档 ──── prompts/strategy-improvement.md
    │  "这次排查有帮助吗？"
    │  更新 memory/strategies.yaml
    │  更新 memory/categories.yaml
    │  全自动策略维护（合并/淘汰/进化，不打扰用户）
    │  受保护策略（pinned + 最近5次使用）不触碰
    │  知识缺口提醒（未注册的服务）
    │  清理临时文件
```

### 10.2 多方案规划与并行策略

问题往往有多个可能的原因或涉及多条调用链路。AI 应当列出所有合理的排查方向，而非只走一条路径。

**10.2.1 方案拆分**

按以下维度拆分独立排查方案：
- **按业务链路**：支付链路 / 订单链路 / 资金链路
- **按可能原因**：缓存问题 / 数据问题 / 配置问题
- **按关键字命中**：SLS 查询返回多条不同调用链路时，每条链路作为独立方案

**示例**：用户说"某笔订单支付异常"

```
排查方向（可多选）：

  A. 支付链路排查
     [sls] payNotify AND {tradeSeq}
     [mysql] t_payment_record WHERE trade_seq = '{tradeSeq}'

  B. 订单链路排查
     [sls] updateStatus AND {orderId}
     [platform] Doris 订单历史表

  C. 资金链路排查
     [mysql] t_user_flow WHERE user_id = {userId}
     [redis] wallet:frozen:{orgId}:{userId}

请选择 [A B C / A+B / 全部]：
```

**10.2.2 并行策略**

| 层级 | 场景 | 策略 |
|------|------|------|
| 方案间并行 | 用户选择 A+B 两个排查方向，A 和 B 互不依赖 | 询问用户是否并行，默认建议并行 |
| 方案间串行 | 方案 B 依赖方案 A 的结果（如需先从 A 获取 ID） | 标注依赖关系，先 A 后 B |
| 方案内并行 | 同一方案中 redis 查缓存和 mysql 查 DB 互不依赖 | 自动并行，无需额外确认 |
| 方案内串行 | 先查用户表获取 user_id → 再用 user_id 查订单 | 自动串行 |

**并行控制**：
- 最大并行数由 `guards/query-limits.yaml` 中 `max_parallel_queries` 控制（默认 3）
- 每个并行任务独立超时
- 任一任务失败不影响其他任务，失败的标记为 `error` 并在结果中展示
- 用户的并行偏好可记入 `memory/confirmations.yaml`（如「默认并行」）

**10.2.3 关键字命中多链路**

当 SLS 查询返回的日志涉及多条不同调用链路时：

```
日志查询发现 3 条链路：
  链路 1: payNotify → confirmPay → updateBalance  [ERROR]
  链路 2: rechargeOrder → doRecharge → addBalance  [SUCCESS]
  链路 3: refundApply → doRefund → deductBalance   [SUCCESS]

是否深入分析所有链路？还是只关注异常链路（链路 1）？
可以并行分析多条链路。
```

### 10.3 环境探查与按需选工具

#### 10.3.1 环境探查（规划前必做）

在规划任何查询之前，AI 必须读取各 adapter 的 `config.yaml`，确认当前可用的工具和环境。

```
当前可用工具：
  platform  → prod（仅线上，无测试环境）
  sls       → prod, test, uat
  mysql     → finance_prod, order_prod, base_test
  redis     → prod_cluster, test_standalone
  elasticsearch → es_prod (6.x)
```

**环境隔离原则**（硬性）：
- 不同环境的数据不能混查（不能用 prod 日志关联 test 数据库）
- `platform` 只有 prod 配置 → 测试环境问题不能用它
- 确定目标环境后，只使用该环境下有配置的 adapter 和 profile
- 查询方案中每步标注 `[adapter → 环境/profile]`

#### 10.3.2 按需选择工具

**核心原则：只选解决问题所需的最少工具，不是把所有 adapter 都用上。**

| 场景 | 正确做法 | 错误做法 |
|------|---------|---------|
| 用户问余额不对 | 查 redis + mysql（代码逻辑涉及这两个） | 把 sls + platform + es 也加上"以防万一" |
| 用户问日志报错 | 查 sls（直接看日志） | 先查 platform 再查 mysql 最后查 sls |
| 测试环境问题 | 只用 test 环境下的 sls + mysql | 混用 prod 的 platform |

选择依据：代码理解（Step 3）→ 代码中涉及了什么数据源就查什么，没涉及的不用。

### 10.4 大结果集与上下文管理

日志查询可能返回上千条记录，直接全量载入大模型上下文会导致溢出或性能下降。采用四层递进策略，由 `guards/context-limits.yaml` 配置具体阈值。

**10.3.1 四层处理流程**

```
查询返回结果
    │
    ▼
Phase 1: 概览统计（不消耗上下文）
    │  只提取：匹配总数、时间分布、级别分布、去重异常类型
    │  告知用户概况
    │
    ▼
Phase 2: 智能采样（控制上下文大小）
    │  采样策略：
    │  - 第一条（问题起点）+ 最后一条（当前状态）
    │  - 所有 ERROR 级别（最多 max_error_sample 条）
    │  - 状态变化点（字段值从 A 变 B 的记录）
    │  - 异常堆栈首次出现（去重）
    │  字段裁剪：只保留 time/level/message/traceId/exception
    │
    ▼
Phase 3: 临时文件（超大结果集兜底）
    │  条件：结果集 > context-limits.yaml 的 temp_file_threshold
    │  完整结果写入 /tmp/investigation/{session_id}/*.jsonl
    │  AI 只在上下文中保留 Phase 2 的采样结果
    │
    ▼
Phase 4: 按需下钻
    用户命令          AI 操作
    "看更多"          从临时文件加载下一批（batch_size 条）
    "看14:30-14:32的"  按时间范围筛选
    "看所有 ERROR"    按级别筛选
    "看第 200-210 条"  按行号读取
    "搜索 xxx"        在临时文件中 grep
    "导出结果"        告知临时文件路径
```

**10.3.2 字段裁剪规则**

SLS 日志字段裁剪（减少 50-70% 文本量）：

| 保留字段 | 说明 |
|---------|------|
| `__time__` | 时间戳 |
| `level` | 日志级别 |
| `message` | 日志内容 |
| `traceId` | 调用链 ID |
| `exception` | 异常堆栈 |
| `request_uri` | 请求路径 |
| `status` | 响应状态码 |

| 丢弃字段 | 说明 |
|---------|------|
| `__source__`、`host`、`pod`、`container` | 基础设施信息，排查时通常不需要 |
| `__tag__:__hostname__`、`__tag__:__path__` 等 | 标签元数据 |

SQL / Redis / ES 结果集同样有行数和字段长度限制，详见 `guards/context-limits.yaml`。

**10.3.3 临时文件管理**

```
/tmp/investigation/
└── {session_id}/                    # 每次排查一个目录
    ├── sls_prod_20260328_143200.jsonl    # SLS 完整结果
    ├── mysql_finance_20260328_143215.jsonl  # MySQL 结果
    └── summary.yaml                     # 概览统计信息
```

- 排查结束后（Step 8）自动清理
- 如果排查中断（用户关闭会话），临时文件保留到下次清理
- 用户说「导出结果」时告知临时文件路径，可自行查看
- 会话上下文中记录临时文件路径（见 11.1 session.temp_files）

### 10.5 错误处理

| 错误类型 | 处理方式 |
|---------|---------|
| 网络超时 | 自动重试 1 次（间隔 3 秒），仍失败则告知用户 |
| 认证失败 | 提示用户检查 `.env` 中对应的环境变量值 |
| SQL 语法错误 | 展示 Doris 报错信息，AI 尝试修正后重新展示给用户确认 |
| 分区表未带 dt_month | AI 自动补充分区条件（从实体中推断月份），不需要用户干预 |
| adapter 未启用 | 告知用户该能力未接入，建议如何启用 |
| 无结果 | 明确告知「未找到数据」，建议放宽查询条件或换个维度 |

## 第十一章：会话上下文管理

一个线上问题很少一次查询就能定位。通常需要多轮交互，每轮查到新线索再深入。会话上下文让 AI 在多轮之间保持连贯，不重复查询、不丢失线索。

### 11.1 会话上下文结构

AI 在排查过程中维护一个内存中的上下文对象（不写入文件，排查结束后丢弃）：

```
session:
  # 基本信息
  problem_description: "用户138xxxx充电后扣费异常"
  scene: "c-side"
  category: "充电订单-支付失败"
  started_at: "2026-03-28T16:30:00"

  # 实体池（逐轮积累）
  entities:
    user_phone: "138xxxxxxxx"          ← 第 1 轮：用户提供
    user_id: 541324                    ← 第 1 轮：从用户表查到
    record_id: 598002873               ← 第 2 轮：从订单表查到
    trade_seq: "3201010..."            ← 第 2 轮：从订单表查到
    dt_month: "2025-03-01"             ← 第 2 轮：从订单时间推断

  # 查询历史（每轮记录）
  queries:
    - round: 1
      adapter: "platform"
      query: "SELECT user_id ... WHERE user_phone = '138xxxx'"
      result_summary: "找到用户 541324，所属机构 vehicle_org_id=100"
      entities_discovered: ["user_id: 541324"]

    - round: 2
      adapter: "platform"
      query: "SELECT record_id, trade_seq ... WHERE uid = 541324"
      result_summary: "最近 5 个订单，其中 record_id=598002873 状态为 4（异常结束）"
      entities_discovered: ["record_id: 598002873", "trade_seq: 3201010..."]

    - round: 3
      adapter: "sls"
      query: "3201010... AND ERROR"
      result_summary: "发现 NullPointerException in PaymentService.confirmPay()"

  # 发现和结论链（逐步建立）
  findings:
    - "用户 541324 最近订单 598002873 异常结束"
    - "支付明细 pay_type=3，paied_amount=0"
    - "SLS 日志显示 PaymentService 抛出 NullPointerException"

  # 临时文件（大结果集写入的文件路径，排查结束后清理）
  temp_files:
    - path: "/tmp/investigation/{session_id}/sls_prod_20260328_143200.jsonl"
      adapter: "sls"
      total_rows: 1283
      sampled_rows: 15

  # 知识缺口（排查中发现未注册的服务，Step 8 时提示用户）
  knowledge_gaps:
    - service: "charge_server"
      reason: "日志中涉及充电服务但 projects/ 中无对应文件"

  # 当前状态
  current_conclusion: "支付确认环节代码异常导致扣费为 0"
  needs_further_investigation: false
```

### 11.2 实体积累机制

每轮查询结束后，AI 从结果中提取新实体并加入实体池：

```
第 1 轮：用户给了手机号 → 查到 user_id
第 2 轮：用 user_id 查订单 → 查到 record_id、trade_seq
第 3 轮：用 trade_seq 查日志 → 查到异常堆栈、traceId
```

实体池中的值可在后续轮次的查询模板中直接替换，无需用户重复提供。

### 11.3 避免重复查询

AI 在规划下一轮查询前，检查 `queries` 历史：
- 如果相同 adapter + 相同查询已执行过 → 跳过，直接使用缓存结果
- 如果查询范围是上一轮的子集 → 从上一轮结果中过滤，无需重新查询

### 11.4 结论推导链

`findings` 列表形成从现象到原因的推导链。AI 在 result-analysis 阶段按时间线组织这些发现，帮助用户理解「因为 A → 所以 B → 导致 C」的因果关系。

最终展示给用户时，以结论推导链为主线，查询数据为支撑证据。

## 第十二章：自我进化机制

自我进化是 skill 从「工具」走向「助手」的关键。但进化必须在用户监督下进行——AI 提案，用户审批，避免失控。

### 12.1 用户反馈闭环

每次排查结束后，AI 主动询问：

```
AI: "这次排查结果有帮助吗？"

选项：
  A. 有帮助，快速定位了问题
  B. 部分帮助，找到了一些线索但没完全定位
  C. 没帮助，方向不对
  D. 跳过，不想评价
```

**反馈驱动的策略调整**：

| 用户反馈 | AI 动作 |
|---------|---------|
| A 有帮助 | 策略 score +1，标记为 high effectiveness |
| B 部分帮助 | 策略 score 不变，但记录「部分命中」便于后续分析 |
| C 没帮助 | 策略 score -1，如果 score 降为 0 则标记为 low effectiveness |
| D 跳过 | 不更新 score |

### 12.2 记忆压缩

memory/ 文件有容量上限，防止无限膨胀降低 AI 的阅读效率。

**触发条件**：strategies.yaml 超过 50 条策略时

**压缩流程**：

```
AI 读取全部策略
    ↓
Step 1: 合并 — 相同 category 下查询步骤高度相似的策略合并为一条
    ↓
Step 2: 淘汰 — 满足以下全部条件的策略标记为待淘汰：
    - effectiveness score < 0.3
    - last_used 超过 30 天
    - 不是唯一覆盖某 category 的策略
    ↓
Step 3: 展示 — 向用户展示合并和淘汰方案
    "以下 3 条策略将被合并为 1 条，以下 2 条策略将被淘汰，确认？"
    ↓
Step 4: 用户确认 → 执行压缩
    用户拒绝 → 保持原样，下次再提醒
```

### 12.3 知识过时检测

Knowledge 层的信息可能因代码变更而过时。AI 通过以下方式检测：

**被动检测**（排查过程中）：
- 使用 knowledge/b-side/pages.yaml 中的路由去前端代码中匹配，发现路由不存在 → 标记 `stale`
- 使用 knowledge/tables/ 中的表结构查询，发现字段不存在或类型变了 → 标记 `stale`
- 使用某个 adapter README 中描述的方法调用失败 → 提醒用户检查

**标记与通知**：
- 过时条目不自动删除，而是标记 `stale: true` + `detected_at`
- 排查结束后提醒用户：「以下知识可能已过时，要更新吗？」
- 用户确认后触发 knowledge-onboarding 重新生成

### 12.4 策略效果评估

AI 定期（每 10 次排查后）生成策略效果报告：

```
AI: "策略效果周报"

使用频率 Top 5:
  1. 充电订单-支付失败 (stg-001) — 使用 5 次，成功 4 次，得分 0.8
  2. B端-页面数据不展示 (stg-003) — 使用 3 次，成功 3 次，得分 1.0
  ...

需要关注:
  - stg-005 "用户余额异常" — 成功率仅 0.3，建议优化查询步骤
  - stg-007 "充电中断" — 30 天未使用，可能已过时

建议:
  - 对 stg-005 增加 SLS 错误日志查询步骤
  - 对 stg-007 下次遇到时验证有效性
```

此报告不自动执行任何操作，只是展示给用户供决策参考。

### 12.5 Prompt 自优化

最高级的进化形式：AI 识别到某个 prompt 的指引不够好时（例如实体提取阶段频繁漏提取某类实体），可以**提案修改 prompt 文件**。

**约束**：
- AI 不能直接修改 prompt 文件
- AI 展示修改提案（diff 形式）给用户
- 用户批准后才写入
- 修改记录写入 memory/audit-log.yaml

这是最谨慎的进化形式——修改 prompt 等于修改 AI 自身的思考方式，必须人工审批。

## 第十三章：项目与知识入驻

### 13.1 统一原则

所有知识文件（projects/*.md、knowledge/**）遵循同一个生产流程：

```
用户给一句话描述 → AI 扫描代码/数据 → 生成代码导航地图 → 展示给用户 → 用户确认 → 落盘
```

用户永远不需要手写知识文件。只需要告诉 AI 「注册 XX 服务」，AI 自动扫描代码生成。

### 13.2 项目注册约定（`projects/_convention.md`）

`projects/` 采用与 `adapters/` 相同的插件化设计：

```
projects/
├── _convention.md          # 项目注册约定（AI 创建新项目时的依据）
├── omp-shop.md             # 前端项目（插件）
├── finance_server.md       # 后端项目（插件）
├── order_server.md         # 后端项目（插件）
└── ...                     # 一个服务 = 一个 .md
```

每个 `projects/<name>.md` 是一个**代码导航地图**，包含四个必要部分：

1. **基本信息**：服务类型、代码根路径、SLS 容器名、关联数据库、所属端、一句话职责
2. **代码导航**：Controller / Service / 数据层的文件路径表（告诉 AI 去哪读活代码）
3. **排查路径**：常见问题 → 入口代码（类#方法）→ 关联 adapter + SLS 日志关键字
4. **元信息**：生成时间、来源、最后验证时间

后端与前端项目采用不同格式，详见 `projects/_convention.md`。

### 13.3 单项目注册工作流（`prompts/project-onboarding.md`）

**触发**：用户说「注册项目」/「注册 XX 服务」/「让 XXX 加入排查」

**流程**：

```
Step 1: 收集基础信息
  AI: "项目叫什么？代码在哪？"
  → 自动在 workspace-index.yaml 中查找路径
  → 找到 → 自动使用，不再追问
  → 找不到 → 请用户提供路径

Step 2: 识别项目类型
  pom.xml/build.gradle → Java 后端
  package.json + src/views/ → 前端 Vue
  requirements.txt → Python 服务

Step 3: AI 深度扫描代码
  Java 后端 →
    - 扫描 **/controller/**/*.java → 提取接口入口（@RequestMapping等注解）
    - 扫描 **/service/**/impl/*.java → 关联业务逻辑
    - 扫描 **/mapper/*.xml → 提取表名和 Mapper 路径
    - 扫描 Redis 操作 → 提取 key 模式
    - 提取日志关键字（log.info/log.error 中的标识符）
    - 推断 SLS 容器名、关联数据库

  前端项目 →
    - 扫描 src/router/ → 路由和页面
    - 扫描 src/api/ → API 定义
    - 扫描 src/views/ → 页面-API 关联
    - 按 URL 前缀推断后端服务

Step 4: 生成代码导航地图
  按 projects/_convention.md 定义的格式，生成完整的 projects/<name>.md
  包含：基本信息 + 代码导航（Controller/Service/数据层路径表）+ 排查路径 + 元信息

Step 5: 展示给用户确认
  AI: "我根据代码扫描生成了 projects/finance_server.md，包含：
    - Controller: 15 个功能域
    - Service: 23 个业务类
    - 数据表: 18 张
    - 排查路径: 8 个常见问题入口
    [展示完整内容]
    确认写入？"

Step 6: 检查关联
  如果注册的是后端服务，检查 projects/omp-shop.md 是否有页面调用了该服务
  → 建议同步更新前端排查路径
```

### 13.7 自适应机制

**知识缺口自动检测**：

- 记录缺口到会话上下文

- 代码路径不存在（文件被移动/重命名）→ 标记 stale，提醒更新

**越用越准**：
排查结束后的策略归档会关联用到的 project 文件：
- 哪些代码路径帮助了定位 → 记录到策略中
- 下次同类问题直接指向有效的代码入口

## 第十四章：Adapter 扩展指南

这是架构最核心的可扩展性保障：AI 能在用户监督下自主新增能力，无需人工写代码。

### 14.1 扩展触发

用户说：「加个 Redis 能力」/「接入 ES」/「我想查 Nacos 配置」

### 14.2 AI 自主创建流程

```
Step 1: 读取约定
  AI 读取 adapters/_convention.md，理解标准结构

Step 2: 收集信息
  AI: "Redis 的连接地址、端口、密码是什么？"
  AI: "主要用来查什么场景？（缓存状态/会话/分布式锁/...）"

Step 3: 创建目录和文件
  AI 按约定创建：
    adapters/redis/
    ├── README.md           AI 根据收集的信息编写
    ├── client.py           AI 按接口规范实现（health_check + 业务方法）
    ├── config.yaml         AI 生成模板，用户填写实际值
    └── requirements.txt    AI 填入正确的依赖包

Step 4: 更新注册表
  AI 在 SKILL.md 的能力注册表中加一行：
    | redis | Redis 缓存查询 | 实时状态排查 | ⏳ 待验证 |

Step 5: 验证连通性
  AI 执行 client.py 的 health_check()
    成功 → 状态改为 ✅ 可用
    失败 → 保持 ⏳ 待验证，展示错误信息给用户排查

Step 6: 展示全部变更给用户确认
  AI: "我创建了以下文件并更新了 SKILL.md："
  [列出新建文件和修改]
  "确认生效？"

Step 7: 用户确认 → 完成
```

### 14.3 无损引入保障

| 保障机制 | 说明 |
|---------|------|
| **目录隔离** | 新 adapter 是独立目录，不触碰任何已有文件 |
| **SKILL.md 最小修改** | 只在注册表加一行，不改流程逻辑 |
| **enabled 开关** | config.yaml 中 `enabled: false` 即可随时禁用 |
| **health_check 守门** | 验证通过才标记为可用，不影响已有能力 |
| **回滚简单** | 删除目录 + 删除注册表对应行即可完全回滚 |

### 14.4 AI 需要的外部知识

AI 创建新 adapter 时，可能需要了解目标数据源的 SDK 用法。处理方式：

- **常见数据源**（Redis、ES、Nacos）：AI 自身训练数据包含足够的 SDK 知识
- **不确定时**：AI 先通过 web search 或 context7 查询最新文档
- **用户提供源码时**：AI 读取用户提供的代码/文档，按照理解实现

### 14.5 预规划的 Adapter

| Adapter | 接入方式 | 排查场景 | 预估 client.py 复杂度 |
|---------|---------|---------|---------------------|
| **redis** | `redis-py` SDK，直连 | 会话状态、分布式锁、缓存数据、计数器 | 低 |
| **elasticsearch** | `elasticsearch-py` SDK | 全文检索历史记录、电费流水 | 中 |
| **nacos** | HTTP API（Open API） | 查看服务配置、灰度开关、配置变更历史 | 低 |
| **mq** (Kafka) | `confluent-kafka` SDK | 消息回溯、消费者 lag、死信队列 | 高 |

每个 adapter 的实际接入时间取决于用户需求，不提前实现。

## 第十六章：Agent 架构与中断控制

### 16.1 主/子 Agent 职责分离

```
用户 ←→ 主 Agent（沟通/规划/确认/同步结果/展示分析）
              ↓ 用户确认方案后
         子 Agent(s)（执行查询，调用 adapter client.py）
              ↓ 逐步回传结果
         主 Agent（汇总展示，更新进度表）
```

| 角色 | 职责 | 不做什么 |
|------|------|---------|
| 主 Agent | 与用户对话、制定方案、展示结果、策略归档 | 不直接调用 adapter |
| 子 Agent | 执行具体查询（SLS/MySQL/Redis/Platform/ES） | 不与用户交互 |

### 16.2 中断控制

**原则：用户的任何新指令，立即覆盖当前排查流程。主 Agent 绝不阻塞等待子 Agent。**

| 用户动作 | 主 Agent 行为 |
|---------|-------------|
| 发送新消息 | 立即响应用户，不再等待未完成的子 Agent |
| 说「停」「算了」 | 终止排查，保留已有结果 |
| 说「跳过这步」 | 跳过当前等待中的步骤 |
| 说「换个方向」 | 丢弃当前方案，回到查询规划 |
| 说「直接给结论」 | 基于已有结果（即使不完整）给出判断 |
| 问了无关问题 | 正常回答，排查上下文自然终结 |

**禁止场景**：用户发了消息，主 Agent 不回复（还在等子 Agent）。

### 16.3 中断点设计

排查流程中的每个步骤转换点都是中断点。具体在 `prompts/query-planning.md` 和 `prompts/result-analysis.md` 的每个 `###` 标题后检查用户是否有新指令。

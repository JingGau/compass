# 已知页面或 BFF 时：入口到链路定位

## 适用场景

已经能从用户描述、页面、BFF 应用、接口路径、前端 API 文件或网关应用确认入口。

典型例子：

- 用户能说出具体页面或按钮。
- B 端页面能通过路由 / API 文件映射到后端接口。
- C 端接口路径已知，如 `/app/gun/payment-ways-v2`。
- 已知道 BFF / 网关应用，但还不知道后端业务分支。

## 排查路径

1. 先记录入口 scene fact
   - 记录页面 / BFF / 接口路径 / 应用名。
   - 如果来自知识库或代码扫描，要写清楚来源。

2. 从入口找日志关键词
   - 优先使用接口路径、Controller 方法名、日志模板、代码常量、请求参数名。
   - 不要自己发明业务关键词。
   - 如果关键词来自代码，SLS gate 使用 `keyword_source=code`；来自 SQL 字段或表结构，使用 `keyword_source=sql/schema/table_field/code_sql`。

3. 用实体锚点 + 入口关键词查链路
   - SLS 查询仍必须有高区分度 anchor。
   - 入口关键词只用于快速缩小链路，不替代 anchor。
   - 用户未给时间时默认最近一周；如果可从订单/支付/事件时间推断窗口，优先使用推断窗口并记录依据。
   - 默认 logstore 使用 `all`；切到单服务 logstore 前必须用户确认。
   - 目标是确认该入口在故障时间窗内实际调用了哪些服务和下游。

4. 分析链路差异
   - 对比入口请求、上游返回、下游响应、最终响应。
   - 关注“上游有 / 下游无”“代码过滤前有 / 过滤后无”“状态推进到哪一步停止”。

5. 回代码确认业务条件
   - 根据链路中的接口、日志模板、类方法定位业务分支。
   - 记录判断条件、过滤条件、状态机分支或配置依赖。

6. 再进入数据或结论
   - 如果代码分支依赖数据库状态，按代码表名和字段走 Doris / JDBC catalog。
   - 如果链路和代码已经闭环，补 hypothesis / conclude。

## 门禁提醒

- 已知入口不等于可以跳过 scene fact。
- 已知接口不等于可以跳过 SLS anchor。
- 入口关键词只能加速定位，不能作为唯一查询条件。
- 代码里的日志模板、字段名、枚举值要作为证据记录，不要只口头引用。

## 证据落点

- 页面 / BFF / 接口映射：scene fact。
- 链路日志：evidence。
- 代码业务分支：evidence。
- 数据状态或配置依赖：后续 SQL evidence。

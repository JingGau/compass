# 直接故障点到最近变更根因

## 适用场景

当排查已经发现某个明确断点，但这个断点只能解释“哪里失败了”，还不能解释“为什么现在失败”时使用。

常见断点包括：

- 设备 TCP / MQTT / HTTP 连接网关失败。
- 服务调用下游超时、拒绝、无响应。
- 校验失败、状态异常、设备离线、心跳中断。
- 数据库、Redis、MQ、第三方接口、证书、DNS、白名单、路由、负载均衡不可达。

典型判断：如果当前结论只写得出“枪连不上网关，所以充电校验失败”，但没有说明最近为什么连不上，这通常只是直接原因或半原因，不应直接当根因。

## 排查路径

1. 固定直接故障点
   - 记录哪个设备、服务、接口、依赖、网关或配置项失败。
   - 写清楚失败表现、错误码、日志关键字、首次发现时间和影响范围。

2. 追最近变更
   - 查发布、配置中心、网关地址、端口、协议、证书、白名单、DNS、路由、负载均衡、设备绑定关系、站点迁移、机房迁移、灰度策略。
   - 如果发现变更，必须用 `change record` 登记到 timeline。
   - 变更来源可以是配置平台、运维工单、发布记录、设备管理后台、代码提交或人工确认。

3. 对齐时间线
   - 对比故障首次出现时间、最后一次正常时间、设备最后心跳或重连时间、配置生效时间、发布/迁移时间。
   - 只有当变更时间能解释故障窗口，才把它提升为根因候选。

4. 扩大和收敛影响面
   - 对比同网关、同站点、同批设备、同配置版本、同服务实例是否异常。
   - 对比未变更对象是否正常，避免把偶发连接失败误判为配置根因。

5. 找反证或恢复证据
   - 回滚配置、修正地址、恢复白名单、换回旧网关或重新绑定后是否恢复。
   - 如果无法实际恢复，至少要给出可验证的反证条件：未变更对象正常、变更对象集中异常、变更时间覆盖故障开始时间。

## 门禁提醒

- 直接故障点不是结论终点；它最多回答“哪里断了”。
- 根因结论必须回答“为什么在这个时间、这个范围突然断了”。
- 不要凭“最近有变更”直接定因；必须同时满足时间线、影响面和机制解释。
- 任何真实日志、SQL、配置查询仍必须走 `action plan -> action complete`。
- 线上 SLS / Doris 查询仍要遵守实体锚点、默认时间窗、logstore=all、EXPLAIN 和用户确认门禁。

## 证据落点

- 直接断点：作为 evidence，说明错误表现、日志或查询来源。
- 最近变更：作为 change，写入类型、目标、描述、时间和来源。
- 时间线对齐：作为 timeline 或 evidence，说明故障开始时间与变更生效时间关系。
- 影响面：作为 evidence，说明异常对象和正常对照对象。
- 反证条件：作为 hypothesis 的 `--falsifiable` 或 conclusion 的 `--unsolved` / `--pattern-scan`。

## 结论质量检查

结论前问三件事：

1. 当前证据是否只证明了“断点”，没有证明“断点为什么出现”？
2. 是否查过最近配置、发布、迁移、绑定、网络或证书变化？
3. 时间线、影响面和恢复/反证是否共同支持这个变化就是根因？

如果第 1 个答案是“是”，且第 2、3 个答案没有证据支撑，应把结论降级为“直接原因 / 待验证根因”，继续补最近变更证据。

推荐表述：

> 直接原因是枪 TCP 无法连接网关，导致充电校验失败；进一步追溯发现该枪近期网关地址从 A 变更为 B，且变更时间覆盖故障开始时间，同批未变更设备正常。因此根因是网关地址变更后设备侧/平台侧配置未同步或新地址不可达，TCP 连接失败是直接表现。

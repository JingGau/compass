# 截图或关键字入口到当时调用日志

## 适用场景

用户提供截图、页面文案、按钮名、报错提示、接口关键字、业务字段名或一小段可搜索文本，但还没有明确完整链路。

典型例子：

- 用户发来 B 端 / C 端截图，能看到页面标题、按钮、弹窗、错误文案。
- 用户只说“页面显示余额不足”“提交后提示校验失败”“订单详情不展示某字段”。
- 用户提供关键字，如接口路径片段、页面功能名、日志中的一段提示、字段名。

## 排查路径

1. 先把截图或关键字转成 scene fact
   - 记录页面、按钮、文案、错误提示、用户实体和时间范围。
   - 如果截图里有敏感信息，进入 evidence / report 前必须脱敏。
   - 截图不能直接当根因，只能作为入口和现象证据。

2. 根据页面或关键字找日志入口
   - 优先从页面路由、BFF/API 文件、接口路径、Controller 方法、日志模板、代码常量中找到可验证关键词。
   - 如果只有页面文案，先尝试在代码或知识库里找到对应接口 / BFF / 后端应用。
   - 不要直接用“失败/异常/订单/支付”等泛词裸扫线上日志。

3. 查当时的真实调用情况
   - SLS 查询必须有高区分度 anchor：手机号、用户 ID、订单号、支付单号、traceId、枪编码、站点名等。
   - 关键词可来自截图/用户原话，但应尽快用代码里的接口路径、日志模板或字段名替代或补强，并声明 `keyword_source`。
   - 用户未给时间时默认最近一周；如果能从订单创建、支付创建或事件时间推断窗口，使用推断时间窗并记录依据。
   - 默认 logstore 使用 `all`；切换到单服务 logstore 前必须用户确认。

4. 从日志命中还原链路
   - 提取 traceId / tlogId / requestId、接口路径、容器/服务名、上下游响应、错误码和关键参数。
   - 重点回答“用户截图那一刻，系统实际调用了什么、返回了什么、在哪里分叉”。

5. 再回代码或数据补证
   - 如果日志显示调用到某个接口或服务，回代码确认业务分支、过滤条件、状态机或配置依赖。
   - 如果代码分支依赖表状态，再按真实表名和字段去 Doris / JDBC catalog 查证。

## 门禁提醒

- 截图和关键字是入口线索，不是根因证据。
- 线上日志查询仍必须先 `action plan --track sls`，查询后 `action complete`。
- 截图/用户原话里的关键词若作为额外查询词，应在 action objective 或 evidence 中说明来源；能从代码确认时，优先升级为 `keyword_source=code`。
- 没看到当时真实调用前，不要直接根据页面表现下结论。

## 证据落点

- 截图/关键字入口：scene fact，记录页面、文案、按钮、提示和来源。
- 日志命中：evidence，记录命中时间窗、query、anchor、trace/tlog 和调用摘要。
- 链路差异：evidence，记录上游请求、下游响应、最终响应或错误码。
- 代码分支 / 数据状态：后续 code / sql evidence。

# 不确定入口时：关键词日志到链路追踪

## 适用场景

用户只给出现象、关键词、用户标识、订单号、手机号、时间段等线索，但不能确定具体页面、接口、BFF 或后端服务。

典型例子：

- 用户说“礼品卡不展示”，但不知道调用了哪个接口。
- 只有手机号 / 用户 ID / 订单号和大概时间。
- 只有异常现象或模糊业务词，需要先找到真实链路。

## 排查路径

1. 先记录 `scene fact`
   - 记录用户可见现象、实体、时间段、可能入口。
   - 如果只有模糊现象，也要把“不确定入口”作为事实记录，而不是直接猜服务。

2. 用高区分度实体扫首轮日志
   - 优先用手机号、用户 ID、订单号、支付单号、traceId、枪编码、站点名等实体作为 SLS anchor。
   - 关键词可以来自用户原话，但线上查询必须控制范围：实体锚点 + 时间窗 + limit。
   - 用户未给时间时默认最近一周；如果订单创建、支付创建或事件时间可推断，使用推断时间窗并写明依据。
   - 默认 logstore 使用 `all`；改用单服务 logstore 前必须用户确认。
   - 执行前必须 `action plan --track sls`，写清楚目标是“定位入口链路或 trace/tlog”。

3. 从首轮命中里提取链路关键字
   - 优先提取 `traceId`、`tlogId`、`requestId`、接口路径、服务名、容器名。
   - 把这些作为 evidence 或 scene fact 记录下来。

4. 用 trace / tlog 查完整链路
   - 第二轮 SLS 查询以 trace/tlog 为 anchor。
   - 目标是还原请求经过的服务、接口、关键业务分支、上下游响应差异。

5. 回到代码确认业务分支
   - 根据链路里的接口路径、类名、日志模板或方法名，到代码中定位 Controller / Service / Mapper。
   - 代码阅读前也要 `action plan --track code`，并记录目标文件/方法。

6. 再决定下一步
   - 如果链路差异已经足够，补 hypothesis 或 conclude。
   - 如果代码指向数据状态，再按表和字段去 Doris / JDBC catalog 查证。
   - 如果链路缺失，回到 scene fact 补入口、对象、上下游或差异。

## 门禁提醒

- 不要用“异常/失败/支付/订单”等泛词裸扫线上日志。
- 额外关键词必须来自用户原话、代码常量、日志模板、SQL 字段或表结构，并声明 `keyword_source`。
- 没拿到 trace/tlog 前，不要把模糊关键词命中当成根因证据。

## 证据落点

- 首轮日志命中：evidence，说明命中数量、时间窗、提取到的 trace/tlog。
- 完整链路：evidence，说明上下游服务和关键响应差异。
- 代码分支：evidence，引用文件/方法/日志模板。
- 新入口或关键对象：scene fact。
